# Zig 0.17 port: output identity and a decode spot-check

The `zig-0.17` branch ports image to Zig 0.17; main stays on 0.16. The
port must not change pixels or encoded bytes, and it should not move
speed. This records how both were checked. plan.md "Zig 0.17" lists the
API changes.

CPU: Intel Xeon @ 2.60 GHz (4 threads). Both bench binaries are
`zig build bench` at ReleaseFast with native CPU (`NIX_ENFORCE_NO_NATIVE=0`),
main at eeff51c on Zig 0.16.0 and the branch on Zig 0.17.0 (LLVM 22),
run from the same corpus (`bench/corpus-gen`).

## Output identity

`bench-image check` hashes every decode and encode output of every op on
the bench corpus. Main's and the branch's lists are identical: 3,722
outputs, every decoder and encoder, every effort and quality row.

The first comparison was not. WebP lossless and lossy-with-alpha encodes
differed on 32 rows. Zig 0.17 reworked `std.sort.pdq`, and the new one
leaves equal elements in a different order. Two encoders sort with ties:
the WebP lossless entropy-image tile sort (`webp/encode_entropy.zig`) and
the GIF quantizer's two box sorts (`gif/quantize.zig`; no GIF row
differed, but its ties are reachable). `src/sort.zig` is Zig 0.16's pdq
(MIT, named in THIRD_PARTY.md), with a test that pins 0.16's order of
equal keys, and those three sorts use it. After that every row matched.
The JPEG XL sorts already break ties by index, and `std.mem.sort` is
stable, so neither depends on pdq's order.

The alternative is to break those ties by index. That makes the bytes
independent of any sort routine but changes them once, on both branches.

## A Zig 0.17 miscompile: signed-to-unsigned `@intCast` marks `trunc nsw`

CI on the branch (GitHub's `ubuntu-26.04` runner, which has no AVX-512)
failed five JPEG unit tests in ReleaseSafe, the `jpeg_encode` fuzz seeds,
and the oracle: jpeg 4,824, jpeg_encode 6,559, and tiff 71 mismatches
(JPEG in TIFF). Every sample from 128 to 255 came out as 127. This host
passed, since its native target has AVX-512 and the vector code takes
other instructions. Built here for `-Dcpu=baseline`, `x86_64_v2`, or
`x86_64_v3`, the same tests fail and the oracle at 20000 gives jpeg 5,490,
jpeg_encode 6,628, and tiff 154 mismatches; `x86_64_v4` passes. Zig 0.16
passes on every CPU.

The cause is Zig's LLVM backend, not LLVM. Zig 0.17 puts `nsw` on the
`trunc` that `@intCast` emits whenever the source type is signed, even when
the destination is unsigned. On a `trunc`, `nsw` says the result
sign-extends back to the source, that is, it fits the destination as a
signed integer. For a cast to `u8` that is false from 128 up, so those
values become poison, and LLVM 22's x86 backend uses the flag to narrow
with `packsswb` (signed saturation) instead of `packuswb`. The IR for
`@intCast` from each type to each type, from
`zig build-obj -Ofast -femit-llvm-ir` (0.16.0 against 0.17.0):

| `@intCast`               | Zig 0.16.0  | Zig 0.17.0      |
| ------------------------ | ----------- | --------------- |
| `i16` to `u8`            | `trunc nuw` | `trunc nuw nsw` |
| `i32` to `u8`            | `trunc nuw` | `trunc nuw nsw` |
| `i32` to `u16`           | `trunc nuw` | `trunc nuw nsw` |
| `u16` to `u8`            | `trunc nuw` | `trunc nuw`     |
| `i16` to `i8`            | `trunc nsw` | `trunc nsw`     |
| `@Vector(8, i32)` to u8  | `trunc`     | `trunc nsw`     |
| `@Vector(8, i32)` to u16 | `trunc`     | `trunc nsw`     |
| `@Vector(16, u16)` to i8 | `trunc`     | `trunc nuw`     |

The `@max(x, 0)` that Zig narrows to an unsigned type gets the same flag
(`trunc nuw nsw i32 to i31`, wrong from 2^30), and `@truncate` from an
unsigned type does not (`trunc` or `trunc nuw`).

What image does: the three vector sites that narrow signed lanes to
unsigned ones above the signed maximum now use `@truncate` of the lanes as
unsigned, which is the same value since the lanes are already clamped:
`jpeg/idct.zig`'s 16-bit store and its `kernel`'s store, and
`jpeg/encode.zig`'s RGB to YCbCr store. They were found from the
optimized IR of the whole test build (every `trunc` with `nsw` on a
vector, by its debug location), not by reading: the other vector sites
narrow to signed types, where `nsw` is right, or clamp with constant bounds,
which Zig narrows to an unsigned type first. Scalar casts carry the same
wrong flag, but no scalar site was seen to miscompile: a scalar
`@intCast(200)` to `u8` followed by `>= 128` still gives true in every
mode, and the unit tests, fuzz seeds, and oracle pass built for
`baseline`, `x86_64_v3`, and native. `just test-cpu` runs the tests built
for baseline and `x86_64_v3`, in `just ci` and in CI.

After the change: the oracle at 100000 inputs, seed 1, has no mismatch in
any of its 24 modules, built for `-Dcpu=baseline` and natively, and
`bench-image check` built for `x86_64_v4` and for baseline gives the same
3,722 outputs as main's native 0.16 build.

### Draft upstream issue (not filed)

**Title:** LLVM backend: `@intCast` from a signed to a narrower unsigned
integer emits `trunc nsw`, miscompiling vector narrowing on x86

**Zig version:** 0.17.0 (LLVM 22), x86_64-linux. 0.16.0 is correct.

**Steps to reproduce:**

```zig
const std = @import("std");
const V = @Vector(16, i16);

noinline fn narrow(in: *const [2]V, out: *[2][16]u8) void {
    var c: [2]V = undefined;
    inline for (0..2) |i| {
        const w = in[i] - @as(V, @splat(384));
        c[i] = @max(@min(w, @as(V, @splat(255))), @as(V, @splat(0)));
    }
    // x86's punpcklqdq and punpckhqdq on 256-bit vectors.
    const lo = @shuffle(i16, c[0], c[1], @Vector(16, i32){ 0, 1, 2, 3, -1, -2, -3, -4, 8, 9, 10, 11, -9, -10, -11, -12 });
    const hi = @shuffle(i16, c[0], c[1], @Vector(16, i32){ 4, 5, 6, 7, -5, -6, -7, -8, 12, 13, 14, 15, -13, -14, -15, -16 });
    out[0] = @as(@Vector(16, u8), @intCast(lo));
    out[1] = @as(@Vector(16, u8), @intCast(hi));
}

pub fn main() void {
    var in: [2]V = .{ @splat(384 + 208), @splat(384 + 208) };
    var out: [2][16]u8 = undefined;
    narrow(&in, &out);
    std.debug.print("{any}\n", .{out[0]});
}
```

`zig build-exe repro.zig -OReleaseFast -mcpu=baseline` (or `x86_64_v2`).

**Observed:** sixteen 127s. **Expected:** sixteen 208s, which 0.16.0 gives
at every optimization level and CPU, and 0.17.0 gives in Debug and
ReleaseSafe, at `-mcpu=x86_64_v4`, or with `-%` in place of `-`. (In a
larger function the same pattern also fails in ReleaseSafe and at
`x86_64_v3`.)

**Cause:** the narrowing `@intCast` lowers to
`trunc nsw <16 x i16> %x to <16 x i8>` (0.16.0: `trunc`). `nsw` on `trunc`
asserts the value fits `i8` as a signed integer, which a `u8` result from
128 to 255 does not, so LLVM is entitled to the signed pack:

```
	pmaxsw	xmm1, xmm4        ; clamp to [0, 255]
	pminsw	xmm1, xmm5
	...
	punpcklqdq	xmm5, xmm2
	packsswb	xmm5, xmm4        ; signed saturation: 208 -> 127
```

Scalars get the same flag (`@as(u8, @intCast(@as(i16, x)))` is
`trunc nuw nsw i16 to i8`; 0.16.0 emitted `trunc nuw`). The flags should
follow the destination: `nuw` when it is unsigned, `nsw` when it is
signed, and both only when the source is unsigned and the destination
signed. Not bisected; no existing issue was found.
