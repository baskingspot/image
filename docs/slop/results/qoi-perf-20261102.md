# QOI decode: INDEX without the index store, runs in 8-pixel stores, 2026-11-02

After `wbmp-qoi-20261101.md`, QOI decode ran 1.47–1.54× Wuffs but
0.79–1.03× Rust's `qoi` crate, furthest behind on index- and run-heavy
images (screenshot_game-3dbrick2 0.36×, testcard 0.70×) and on 64×64
icons (about 0.55×). Chunk counts of those files (a script over the
stream): 3dbrick2 is 78% INDEX chunks and 21% runs, which cover 81% of
its pixels; testcard is 36% INDEX and 31% runs; kodim01, for contrast,
64% LUMA and 17% INDEX. On 3dbrick2 the decoder took 7.2 ns a chunk, the
crate 2.6.

The QOI specification stores every decoded pixel at its hash in the index.
For two kinds of chunk that store never changes anything:

- An INDEX chunk reads entry `k`, and entries are only ever written at
  their own hash, so entry `k` holds a pixel whose hash is `k` and the
  store writes it back. The exception is an entry never written: it is
  zero, whose hash is 0, so the pixel goes to entry 0. The decoder now
  takes INDEX as its own branch, ahead of the table, writes the pixel, and
  stores only `index[0] = 0` when the pixel is zero. Through the table,
  every chunk stored at `hash(px)`, an address that for INDEX hangs off
  the load just made, and the next chunk's index load has to be ordered
  after that store. (The host exposes no performance counters, so the
  mechanism is inferred; the timing is measured.)
- A run repeats the pixel before it, which the chunk before stored. Only a
  run that starts the image repeats a pixel never stored, so `pixels`
  stores the starting pixel when the first byte is a run, and runs store
  nothing.

Runs also fill 8 pixels a store instead of 16. Storing all of a run's
pixels with four 16-pixel stores and no branch on its length (q3 below),
or two then the loop (q4), was slower, both on run-heavy screenshots and on
photos.

The 64×64 `small` threshold is unchanged, waiting for the bench row that
rotates through distinct icons (on `wave2-harness2`).

Tests: `zig build test` (107). The new test "an INDEX chunk of an entry
never written stores its zero pixel" decodes, at 3×1 (the branchy loop)
and 64×64 (the table loop), a pixel that hashes to 0, an INDEX of an
empty entry, and INDEX 0, which must read the empty entry's zero pixel;
with the `index[0] = 0` store removed from the table loop it fails.

## Method

The exploration (`explore.txt`) used `qrun.sh`: `bench-image serve` on ten
files, each variant in turn, 3 rounds of 100 ms samples on core 3, the
median. Variants: q0 is origin/main 9caf0db; q1 INDEX first without its
store; q3 and q4 the run stores above on q1; q5 q1 without the run store
and with INDEX skipping the store in the branchy loop too; q6b8 and q6b4
q5 with 8- and 4-pixel run stores. q6b8 shipped:

| variant | geomean over q0 (10 files) | 3dbrick2 | testcard  | wikipedia-001 | dice |
| ------- | -------------------------- | -------- | --------- | ------------- | ---- |
| q1      | 1.15–1.17                  | 1.75     | 1.22–1.36 | 0.92–0.96     | 0.93 |
| q3      | 0.95                       | 0.90     | 1.30      | 0.77          | 0.95 |
| q4      | 1.08                       | 1.29     | 1.34      | 0.87          | 0.99 |
| q5      | 1.20–1.22                  | 1.82     | 1.39–1.43 | 1.01–1.02     | 0.96 |
| q6b8    | 1.29                       | 2.08     | 1.44      | 1.05          | 1.01 |
| q6b4    | 1.28                       | 2.11     | 1.41      | 1.06          | 0.98 |

The A/B (`ab/`): `ab.sh` from `convert-tails-20261102/`, `qoi-decode` (to
RGBA8) and `qoi-decode-bgra` over the 44 files, arms interleaved, 10
rounds pinned to core 3, 50 ms a sample, with benchstat and peak RSS.
`image` is this change, `before` origin/main 9caf0db; then Wuffs, qoi.h,
the `qoi` crate (the `image-rs` arm), and zune-qoi. Every arm's checksums
match on every row. An oracle run ran on core 2 meanwhile.

CPU: Intel Xeon Processor @ 2.60GHz (3.3 GHz under load), 4 vCPUs,
AVX-512, a shared cloud host; Linux 6.1, Zig 0.16.0 ReleaseFast for this
CPU, C arms `cc -O3 -march=native`, Rust `target-cpu=native`.
