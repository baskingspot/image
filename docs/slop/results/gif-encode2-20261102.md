# GIF encode follow-ups, 2026-11-02

The follow-ups from `gif-encode-20261102.md`: one pass over the pixels on
the exact path, selective dithering, and quantizer setup on icons.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host where single runs swing by ±10–30%, so only paired, interleaved ratios
are steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU.

Method: interleaved A/B rounds of two builds of bench-image on one core
(`ab.py`: `taskset -c 3`, the bench's `serve` protocol, each call sized to
about 40 ms, the order alternating each round), the median ratio per input,
and the geometric mean by size class (icon up to 4,096 pixels, 1mp up to a
megapixel, large above). Ratios are B's throughput over A's. Raw output is
in `gif-encode2-20261102/`.

## One pass on exact frames

An exact frame (at most 256 colors) was read twice: once to count its
colors into the color set, and again to map each pixel to its index in
that set for LZW. Builds that stop early split an exact encode's time
(`one-pass.txt`): counting is 19–24% of it past icons, mapping as much
again, and LZW the rest, 52–60%.

Counting already finds each pixel's index, so it now keeps the indices in
memory an exact frame leaves idle: the quantizer's tables (2.4 MiB), or 256
bytes for an image too small to quantize. LZW reads them back. Rows past
what fits, in images over about 2.4 megapixels, are converted and mapped
again as before. Work memory does not change (256 bytes more for images of
at most 256 pixels), and the files are byte-identical (`bench-image check`
on all 26 encode inputs).

| row, class           | inputs | B/A                     |
| -------------------- | ------ | ----------------------- |
| gif-encode-few/icon  | 4      | 1.141                   |
| gif-encode-few/1mp   | 4      | 1.253                   |
| gif-encode-few/large | 3      | 1.137                   |
| gif-encode, all      | 11     | 0.98–1.01               |
| gif-encode-anim      | 4      | 0.995–1.010 (11 rounds) |

The large class gains less because two of its three inputs (8 and 16
megapixels) keep only 2.4 megapixels of indices. An image-sized index
buffer would make them one pass too: 1.149× more on the large class, and
nothing elsewhere, for a byte a pixel of work memory (16 MiB on the
16-megapixel mosaic, whose peak RSS would go from 130 to about 146 MiB,
giflib's). That trade is not taken; the owner may want it.

The LZW encoder itself was tried two ways on the indices of four of the
`few` inputs (a scratch harness, best of 15, interleaved 8 times): state
kept in locals with a cached code width and output written a word at a
time was 0.90–0.95× as fast, and a table of four slots a code instead of
two 0.87–1.01×. Neither is taken.
