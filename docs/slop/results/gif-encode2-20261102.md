# GIF encode follow-ups, 2026-11-02

The follow-ups from `gif-encode-20261102.md`: one pass over the pixels on
the exact path, selective dithering, and quantizer setup on icons.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host where single runs swing by ±10–30%, so only paired, interleaved ratios
are steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU.

Method: interleaved A/B rounds of two builds of bench-image on one core
(`ab.py`: `taskset -c 3`, the bench's `serve` protocol, each call sized to
about 40 ms, the order alternating each round), the median ratio per input,
and the geometric mean by size class (icon up to 4,096 pixels, 1mp up to a
megapixel, large above). Ratios are B's throughput over A's. Raw output is
in `gif-encode2-20261102/`.

## One pass on exact frames

An exact frame (at most 256 colors) was read twice: once to count its
colors into the color set, and again to map each pixel to its index in
that set for LZW. Builds that stop early split an exact encode's time
(`one-pass.txt`): counting is 19–24% of it past icons, mapping as much
again, and LZW the rest, 52–60%.

Counting already finds each pixel's index, so it now keeps the indices in
memory an exact frame leaves idle: the quantizer's tables (2.4 MiB), or 256
bytes for an image too small to quantize. LZW reads them back. Rows past
what fits, in images over about 2.4 megapixels, are converted and mapped
again as before. Work memory does not change (256 bytes more for images of
at most 256 pixels), and the files are byte-identical (`bench-image check`
on all 26 encode inputs).

| row, class           | inputs | B/A                     |
| -------------------- | ------ | ----------------------- |
| gif-encode-few/icon  | 4      | 1.141                   |
| gif-encode-few/1mp   | 4      | 1.253                   |
| gif-encode-few/large | 3      | 1.137                   |
| gif-encode, all      | 11     | 0.98–1.01               |
| gif-encode-anim      | 4      | 0.995–1.010 (11 rounds) |

The large class gains less because two of its three inputs (8 and 16
megapixels) keep only 2.4 megapixels of indices. An image-sized index
buffer would make them one pass too: 1.149× more on the large class, and
nothing elsewhere, for a byte a pixel of work memory (16 MiB on the
16-megapixel mosaic, whose peak RSS would go from 130 to about 146 MiB,
giflib's). That trade is not taken; the owner may want it.

The LZW encoder itself was tried two ways on the indices of four of the
`few` inputs (a scratch harness, best of 15, interleaved 8 times): state
kept in locals with a cached code width and output written a word at a
time was 0.90–0.95× as fast, and a table of four slots a code instead of
two 0.87–1.01×. Neither is taken.

## Selective dithering

Bounded Floyd-Steinberg makes photos 20% larger than no dithering on
decision 6's corpus (the 16 truecolor images, `gif-encode-20261102.md`,
scored the same way: PSNR, PSNR after a σ=1 blur of both images, and SSIM,
from ImageMagick's `compare`). The aim was to cut that without giving up
the blurred PSNR dithering is for. Each scheme changes which pixels pass
their error on (`dither-sweep.txt`, means over the 16 images, bytes
summed):

| scheme                                 | PSNR dB | blurred dB | SSIM   | bytes     |
| -------------------------------------- | ------- | ---------- | ------ | --------- |
| bounded Floyd-Steinberg (main)         | 39.01   | 51.16      | 0.9714 | 7,040,569 |
| less error across edges (best of four) | 39.26   | 50.93      | 0.9718 | 7,024,137 |
| no error when it is within 2           | 39.19   | 50.73      | 0.9728 | 6,905,734 |
| no error when the pixel is within 1    | 39.37   | 51.07      | 0.9742 | 6,949,968 |
| no error when the pixel is within 2    | 39.79   | 50.19      | 0.9775 | 6,670,745 |
| three quarters of the error everywhere | 40.10   | 49.83      | 0.9788 | 6,753,325 |
| no error when the pixel is within 4    | 40.40   | 48.33      | 0.9823 | 6,150,491 |
| no dithering                           | 41.11   | 46.87      | 0.9860 | 5,874,489 |

- **Edges are not where the bytes are.** Passing less error across a
  horizontal edge (neighbors differing by 16 to 64 a channel, half or none
  of the error) saves 0.2–0.4% and costs up to 0.7 dB blurred. Texture
  hides banding, but its indices are noisy with or without dithering.
- **The bytes are in smooth areas**, which is where dithering earns its
  blurred PSNR. Every scheme that dithers them less, a dead zone of 2 or
  more or a weaker diffusion, moves along the line from dithering to none:
  about 0.3 dB of blurred PSNR per 100 KB saved, no better than choosing
  `.none` for some images.
- **A dead zone of 1 on the pixel's own color is nearly free.** A pixel
  within 1 a channel of its entry is that color for every purpose; passing
  its unit of error on only flips its neighbors between two adjacent
  entries. Without it: 1.3% fewer bytes, PSNR +0.36 dB and SSIM +0.003
  better, blurred PSNR −0.09 dB. Per image, PSNR and SSIM improve on all
  16, bytes fall on 15, and blurred PSNR moves −0.68 to +0.12 dB (the game
  screenshot most); crops of the two worst at 4× show no banding. This is
  the change.

On the bench rows (`dead-zone-sizes.txt`), files are 0.6% smaller in total:
graphics most (the 600×600 PNG clip art 14.1%, the 512 icon 5.4%, the game
screenshot 5.9%, the sprite animation 3.4%), photos 0.1–0.5%. Speed is
unchanged (`dead-zone-ab.txt`, 13 rounds: 0.97–1.05× by class, 1.01×
overall).

## Quantizer setup on icons

A quantized 32×32 icon took about 255 µs to encode, 200 µs of it in Wu's
quantizer (`icon-variants.txt`, a scratch harness timing `gif.encode` on
the two quantized icons of `gif_encode/true`): 69 µs building the
cumulative table, which is 33³ cells whatever the image size, and 131 µs
cutting boxes. An icon's histogram is sparse (at most 4,096 of 32,768 cells
hold pixels), so most of each box is empty cells, and every cut scanned
every plane of its box on all three axes. Two changes, neither of which
changes a palette (`bench-image check` identical on all 26 encode inputs):

- **Shrunk boxes.** After a cut, each half is shrunk to the cells that
  hold its pixels on the cut axis, found by bisection on the cumulative
  sums (which only grow along an axis); the first box is shrunk on all
  three. A dropped plane has no pixels on one side, so it could never win
  a cut, and the box's sums do not change. Shrinking all three axes after
  every cut cost more in bisection than it saved on the 64×64 icon.
- **A narrow table.** For a frame of at most 16.8 megapixels no count or
  channel sum reaches 2^32, so the table holds them in `u32` (with the
  squared sums still `u64`): 24 bytes a cell instead of 40, written in
  place over the histogram, and box sums exact in wrapping arithmetic. The
  cumulative pass went from about 61 to 47 µs. A unit test checks that the
  narrow and wide tables give the same palettes; one that stores the
  squared sums narrow fails it.

| build (µs a call, median of 15 interleaved rounds) | 32×32 | 64×64 |
| -------------------------------------------------- | ----- | ----- |
| before                                             | 257.8 | 358.8 |
| shrunk on all axes, narrow table                   | 207.6 | 329.4 |
| shrunk on the cut axis, narrow table (the change)  | 203.5 | 307.6 |

On the bench rows (`icon-ab.txt`, 9 rounds): gif-encode/icon 1.164×,
gif-encode-anim/icon 1.176× (its four 64-pixel frames are each quantized),
and the larger classes 0.99–1.02×.

What is left on the 32×32 icon is about 165 µs of Wu: 45–55 µs for the
table, about 85 µs for 3,678 plane evaluations in 255 cuts, 20 µs of
bisection, and 14 µs choosing the next box. A branchless plane scan
(empty sides as 0/0 = NaN, which never compares better) was slower, 224
against 203 µs. Mapping, dithering, and LZW take about 27 µs. giflib's
median cut is still faster here; a different quantizer for small images
would change the palettes, and decision 6 chose Wu for quality.
