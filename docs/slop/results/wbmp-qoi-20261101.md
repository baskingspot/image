# Wave 1: WBMP, the QOI encoder, and QOI decode, 2026-11-01

`just bench-compare` for WBMP decode and encode and QOI decode and encode,
and the interleaved A/Bs behind the QOI decoder's changes. Throughput is
megapixels per second of image; a ratio is this package's throughput over
the arm's (above 1, ours is faster), the geometric mean over a size class of
each row's median paired ratio over 10 rounds. Size classes: icons up to
64×64, up to a megapixel, and larger.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host; single samples vary by ±5–30%, the paired ratios much less), Linux
6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3 -march=native`,
Rust `target-cpu=native`. Raw output: `wbmp-qoi-20261101/after/` (this
branch on 0d5385a: `config.txt`, `rss.txt`, `benchstat.txt`, `summary.txt`,
`rows.txt`, `raw-<arm>.txt`, and the checksum differences of the `own`
operations in `check-diff-<arm>.txt`), `before/` (QOI decode at `origin/main`
5d30f5c, run the same afternoon), and `ab/`.

All of ours is the inputs and outputs every arm holds alike: no decoder or
encoder here allocates or takes work memory. Their state is on the stack:
the QOI decoder's index and pixel (264 bytes) and a 1 KiB conversion span,
the QOI encoder's the same and a span of up to 1 KiB, WBMP's a 256-byte
gray span to decode and 576 bytes to encode. qoi.h allocates its output;
ImageMagick allocates its own image.

## QOI decode: what changed, and the A/Bs

Each variant was built as its own `bench-image` (`ab/build.sh`) and timed
with `ab/run.sh`: `bench-image bench qoi-decode` for every variant in turn,
the order rotating each round, pinned to the last core, then benchstat. A
is `origin/main`. The exploration rounds (`ab/explore-N.txt`, 4–6 rounds of
30–40 ms samples) compared:

| variant | change                                                                           | geomean vs A | notes                                                                                |
| ------- | -------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------ |
| W       | packed buffers decode as one span                                                | +6 to +7%    | icons 16–32 +15 to +40%, nothing slower (explore-1, 2)                               |
| S       | test the tag before RGB and RGBA                                                 | −21%         | icons −40% (explore-1)                                                               |
| F       | runs fill 16 pixels per store                                                    | +8%          | run-heavy rows 2–3×, photos −8 to −13% (explore-1)                                   |
| WF      | W and F                                                                          | +18%         | photos −5 to −10% (explore-2)                                                        |
| WF3, W3 | runs handled outside the inner loop                                              | +6%, −8%     | the reader's `fill` and `toss` per run cost photos (explore-2)                       |
| X, Y    | W, F, and no branch per chunk kind (ops table); Y with `u32` state               | +27%         | photos +12 to +40%, icons 16–32 −7 to −29% (explore-4, 5)                            |
| Z       | Y with the chunk length by arithmetic                                            | +17%         | the table is faster (explore-6)                                                      |
| H       | Y, and below 64×64 a branch per kind with the run test first                     | +23%         | icons still −9 to −46% (explore-7)                                                   |
| H2      | Y, and below 64×64 a branch per kind in wave 0's order (RGB, RGBA, then the tag) | +40%         | **shipped**; icons 16–32 +44 to +73% (explore-8)                                     |
| H3      | H2 with the branchy loop at 64×64 too                                            | +43%         | 64×64 icons +15 to +30% but the 64×64 texture −45% (explore-9)                       |
| V, V2   | H2, and a fast loop writing 8 copies per chunk so runs up to 8 need no branch    | +32%, +17%   | index-and-run screenshots +40 to +50%, long runs and 64×64 icons slower (explore-10) |

The shipped change against A, 10 rounds of 50 ms samples
(`ab/final-decode/`, `ab/final-bgra/`):

- `qoi-decode`: **+37.1%** geomean (280.5 → 384.6 MP/s). 16×16 and 32×32
  icons +44 to +64%; photos +8 to +37% (two within noise); screenshots
  +5 to +61%; the run-heavy rows 2–4×. One row slower: the 64×64 address
  book icon, −9.4%.
- `qoi-decode-bgra`: **+29.0%** (251.8 → 324.7 MP/s), the same pattern; the
  same icon −12.9%.

Wave 0's three follow-ups:

- **Runs** (a memset was 2× on run-heavy rows and 3–9% slower on photos):
  closed. With whole-image spans and 16-pixel block stores, run-heavy rows
  are 2–4× and photos are faster, not slower, because the table loop took
  the per-kind branches off them.
- **Per-call setup on 16×16**: closed by whole-image spans, which skip the
  per-row span setup; 16×16 decodes went from about 0.95 µs to 0.6 µs,
  ahead of qoi.h (1.41× on the 16×16 address book icon) and level with the
  `qoi` crate (1.06, within noise).
- **Photos against the `qoi` crate** (0.75–0.85): the cause was
  mispredicts, not branch order. The table loop brings photos to 0.90–1.11
  of the crate and the 50-megapixel mosaic to 1.00.

What is left, from `after/rows.txt`: the `qoi` crate is still ahead on
index-and-run-heavy images (screenshot_game-3dbrick2 0.36,
3dcursedlabyrinth 0.59, testcard 0.70) and 64×64 icons (0.53–0.57). On those,
runs are 20–30% of the chunks at random, so the table loop's one branch,
on runs, mispredicts. Variant V removes it for runs up to 8 and gains
40–50% there, but loses as much on long runs and 64×64 icons; making both
cases fast is the next target. A likely reason the branchy loop wins below
64×64, not verified: the benchmark decodes one small file over and over,
and the branch predictor learns its few hundred chunk kinds by heart. A
bench row that rotates through many distinct icons would settle whether the
threshold is tuned to that.

## QOI encode

Byte for byte qoi.h's on all 44 inputs (`qoih 44 rows, 0 differ`; zune-qoi
also writes qoi.h's bytes), and on every corpus file and fuzzed stream in
`just oracle` (test/oracle/qoi_encode.zig). The `qoi` crate writes other
bytes of the same length on every input (`after/check-diff-image-rs.txt`),
an index chunk where qoi.h ends a one-pixel run with a run chunk, so
`qoi-encode` is `own`. Speed: 1.49–1.59× qoi.h, which allocates its output,
0.93–1.06× the `qoi` crate writing into the caller's buffer (level within
the machine's spread across two runs), 2.5–3.4× zune-qoi. The encoder needs no work memory and streams into the writer.

## WBMP

Decode is 48–114× Wuffs to gray and 11–26× to RGBA: one table load and one
8-byte store per input octet, against Wuffs's pixel-at-a-time swizzle. At
large sizes it is bound by writing the output (17 GP/s is 17 GB/s of gray).
Encode has no bar library; ours is 1500–2200× ImageMagick's coder, whose
per-call setup and pixel cache dominate, and which thresholds differently
(docs/slop/wbmp.md), so `wbmp-encode` is `own`
(`after/check-diff-magick.txt`, 35 of 44 rows differ). ImageMagick's
decode is 280–400× slower than ours.

