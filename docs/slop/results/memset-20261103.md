# memset: compiler_rt's byte loop, and a shared vector fill

`@memset` of a runtime length, and the zeroing LLVM emits for a large
aggregate (`= @splat(0)`, a union's `.none`, a comptime-length clear over a
few hundred bytes), become a call to `memset`. Zig 0.16 links
compiler_rt's (`lib/zig/compiler_rt.zig`, `memset`): one byte per store,
unrolled by 8. It does so even in a program that links libc: in
`bench-image`, `nm` shows `t memset` at the address of
`compiler_rt.memset`, so glibc's is never called. memcpy and memmove are
compiler_rt's fast versions. Users' binaries get the same memset.

CPU: Intel Xeon @ 2.60 GHz (4 threads, AVX-512), Zig 0.16.0 ReleaseFast
native. Profiles and A/Bs pinned to one core (`taskset`).

## The fill

`src/fill.zig`'s `fill(T, dst, value)` stores a vector at a time, 256 bits
at most, and ends with one store that overlaps the last full one; below a
vector's length it is `@memset`. Two details make it work:

- The stores are volatile. LLVM's loop idiom pass turns a plain loop of
  vector stores back into a call to `memset`.
- They go through a pointer to `@Vector`, reinterpreted from the
  bounds-checked `dst[i..][0..lanes]`. A volatile store of an array is
  split into one store per element, which was half compiler_rt's speed.

512-bit stores were 2–5% slower than compiler_rt's on WebP's images from
64×64 up (the WebP lossless orb's measurement), so the width is capped at
32 bytes, as kernels here keep to 256 bits. No unchecked pointer
arithmetic: every store's slice is checked in safe builds.

Throughput, best of 5, one core (`fill-micro.zig`, output in
`fill-micro.txt`):

|  bytes | `@memset` (compiler_rt) |               `fill` |
| -----: | ----------------------: | -------------------: |
|     16 |                4.1 B/ns | 4.1 B/ns (`@memset`) |
|     64 |                     5.1 |                 57.8 |
|  1 KiB |                     5.6 |                 82.1 |
|  4 KiB |                     5.6 |                 90.1 |
| 64 KiB |                     4.9 |                 43.7 |
|  1 MiB |                     4.9 |                 37.4 |
|  8 MiB |                     4.7 |                 24.3 |

## The call sites

Switched, each a large or per-call fill the profile found:

- BMP: `dib.rle`'s clear.
- ICO: the picked PNG decoder moves out of the `picked` union into its own
  `undefined` field, so `init` zeroes nothing large. Not a fill: the
  zeroing came from the union's initial value.
- JPEG decode: `huffman.Table.init`'s three clears; `frameOf`'s
  coefficient clear.
- JPEG encode: `Codes.init`; `optimal`'s three arrays; `storedScan`'s
  counts.
- TIFF: `fax.render` and `setBits`; `encode_lzw.State` clears.
- GIF encode: the LZW table (init and reset); the ditherer's error rows;
  `ColorSet.reset`.
- WebP lossless encode (the 15 sites its orb listed, and `rankModes`'
  `Analysis` clear): the two hash-head clears, the cache scratch and
  cache, `Histogram.clear`, `buildLengths`' `lens` and radix `at`, the
  clustering's `dense` and `seen` and `compact`'s map, the transforms'
  `hist` and `acc`, `ColorTable.vals`, and `rankModes`' `idx`.
- JPEG XL: a zero-bit context map (`readContextMap`), at the JPEG XL orb's
  request. Main's bench rows do not reach it enough to show (0.1% in the
  profile, no significant change below).

Kept as `@memset`: short and comptime-small fills (palette tails, single
pixels, rows of a few bytes), and TIFF PackBits runs: switching them made
tiff-decode-packbits 3% slower (0.945 against 0.966 with the change
reverted, below).

The gains are largest on small images, where a per-call clear is a large
share: tiff-encode-lzw 2.1–2.2× on 16×16 icons, ICO 2× on 16×16, JPEG
decode up to 1.8× on small files. The few slower rows outside PackBits
(0.8–3%) are images of 256×256 and larger.

Layout noise: qoi-decode, whose code is unchanged, reads 0.975. A second
A/B after reverting the PackBits switch (`ab2-*.txt`) gives
tiff-decode-packbits 0.966 (20 rows slower) and qoi-decode 0.972, with
neither row's code changed, and png-decode 1.006. So a change of 3% or
less on one op is within what moving code around does to this binary,
and is not claimed.

Memory: unchanged. The fill writes the same bytes the `@memset` did, and
ICO's decoder keeps the same fields at the same size.

## Not changed here

- WebP lossy decode (`vp8.decodeFrame`, 4.5%) and WebP animation (4.9%):
  the WebP lossy orb's files, and below the bar for touching a busy
  format.
- JPEG XL VarDCT planes (`readPassGroup`, 4.3–5.5%): the JPEG XL orb is
  removing that clear.
- compress's `flate.Writer.initInPlace` (about 1% of deflate encodes):
  a baskingspot/compress change.
- A caller's own fills (`bench/zig/gif.zig`'s disposal, 3% of
  gif-decode-anim) get compiler_rt's memset too; the fill is not public.
