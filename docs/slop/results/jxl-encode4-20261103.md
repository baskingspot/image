# JPEG XL lossless encode, stage 4, 2026-11-03

Stage 4 of `image.jxl.encode` (`wave5-jxl-encode4`): icon speed, prefix
codes for small images, then the apple.com gap. Stage 3 is
`jxl-encode3-20261102.md`; the method (corpus totals through a scratch
program, A/Bs through `convert-tails-20261102/ab.sh`) is unchanged.
docs/slop/jxl-encode.md has the design.

| commit | change                                                      |
| ------ | ----------------------------------------------------------- |
| count  | tree learning counts samples faster; the files are the same |

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host, so only paired ratios are steady), Linux 6.1, Zig 0.16.0 ReleaseFast
for this CPU; libjxl 0.12.0, `cc -O3 -march=native`, one thread.

## Count: icon speed

`perf record` of the scratch encoder on a 64×64 icon at default (300
encodes, 24 ms each) put 55% of the time in one loop: counting each
sample's token per property bucket and predictor, before the split scan.
Per sample it walked every property, skipped those without thresholds,
and for each predictor loaded the sample's token through `toks` and
`amap` again; it also kept a 64-bit mask per row of counts up to date
with a second read-modify-write. Now (`Count` in encode_modular.zig):

- the sample's column in each predictor's row is computed once, before
  the property loop;
- the loop walks a list of the properties that have thresholds;
- with one or two predictors judged (fast and default), the predictor
  loop is unrolled;
- the masks are gone: the scan finds a row's nonzero entries with a
  16-lane compare, and clearing walks buckets instead of samples.

The first change is most of it: the token loads went through slices the
compiler could not prove apart from the counts it was writing, so they
were reloaded for every property. Every file is byte for byte the same
(every corpus file at every effort, by md5, and 0 of 129 bench rows
differ).

## Prefix codes for small images: not kept

The entropy coder writes prefix codes (Brotli's format) as well as ANS.
A prefix code has no 32-bit final state per stream and its histograms
cost differently, so on a small image it can come out smaller. A trial
built both codes for images of at most 2^22 tokens, estimated each one's
bits (the code written to scratch, plus `Code.cost` of the stored tokens
and 32 bits a stream for ANS), and kept the smaller:

| effort  | before     | prefix trial | files that changed |
| ------- | ---------- | ------------ | ------------------ |
| fast    | 15,575,114 | 15,575,096   | 2 icons            |
| default | 14,441,994 | 14,441,978   | 2 icons            |
| best    | 14,140,396 | 14,140,379   | 2 icons            |

Only two 16×16 icons took prefix codes (664 to 661 and 691 to 678 bytes
at default). Limited to 2^14 tokens, the trial still cost 6–10% of an
icon's time (16×16: 1.1 to 1.2 ms; 64×64: 14.2 to 15.2 ms), for 0.5–2%
on two files. Not kept.

## apple.com: sample coverage

After stage 3, default's apple.com file was 1.043 of cjxl e7's. cjxl's own
options (`apple/cjxl.txt`) show where e7's size does not come from: with
the gradient predictor only (`-P 5`) it writes 1,135,325 bytes, still
smaller than our 1,155,523 with four predictors; previous-channel
properties are off at e7 (`-E 0` is the same file); `-I 100`, learning
from every pixel, is 0.5% smaller than its default, and `-I 50` the same
as its default. Our default learns from 2^18 samples, 1% of this image's.
Variants of ours on apple.com (`apple/variants.txt`):

| default variant         | apple.com bytes |
| ----------------------- | --------------- |
| as is                   | 1,155,523       |
| 4096 leaves (was 1024)  | 1,165,205       |
| 64 thresholds (was 32)  | 1,143,770       |
| 2^20 samples (was 2^18) | 1,128,712       |

So it is coverage. Decision 70 kept 2^18 samples at default for every
image (2^19 cost 28% of the time for 1.16%). Scaling the samples with the
image instead, `clamp(pixels × 4 / k, 2^18, 2^20)`, touches only the
largest files:

| k   | corpus bytes | change | corpus time, before → after | apple.com | amazon.com | cnn.com   |
| --- | ------------ | ------ | --------------------------- | --------- | ---------- | --------- |
| —   | 14,441,994   |        |                             | 1,155,523 | 2,550,179  | 1,079,990 |
| 64  | 14,436,410   | −0.04% | 24.4 → 24.2 s               |           |            |           |
| 32  | 14,388,640   | −0.37% | 24.4 → 24.4 s               | 1,135,111 | 2,522,610  | 1,074,617 |
| 16  | 14,358,338   | −0.58% | 23.3 → 25.0 s (+7.5%)       | 1,128,712 | 2,519,308  | 1,065,901 |

(Each variant ran beside an unchanged build on another core, the k = 64
and 32 runs together, so only times within a row compare.)

At k = 16, apple.com is 1.019 of e7's and the corpus 0.984 of e7's total;
the time goes to the three screenshots and the 1.2–1.4 MP photos. That is
a change to decision 70's terms, so it is not on this branch; it is the
owner's choice.

Profile of apple.com at default (`perf`, two encodes, 3.5 s each): 64%
of the time is tokenizing, and 42% of the total is the weighted
predictor's prediction in it (`modular.Wp.predict`, the decoder's); 8%
sampling, 8% ANS writing, 8% scoring the groups' transforms; tree learning
is under 3%.

## Gates

`just test` and `just lint` exit 0 on the final tree; `rg setRuntimeSafety
src` is empty. `just fuzz 600 "" jxl_encode` (cores 0–1, beside the A/B):
7,744 inputs in 603 s (5,824 in stage 3, at the same 600 s), 0 findings,
exit 0. `just oracle 100000 1 jxl_encode` (cores 0–2): 74,906 agree, 0
mismatches, 163.5 s, exit 0. Both ran before the counting loop moved into
`Count`, a restructuring that writes the same bytes (checked by `cmp` at
every effort) at the same speed.
