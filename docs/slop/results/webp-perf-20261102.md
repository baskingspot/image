# WebP decode performance pass, 2026-11-02

Speed work on `image.webp.Decoder` against libwebp 1.6.0, toward at least
1.0× libwebp in every size class for lossless and lossy decode, with peak RSS
no worse. results/webp-20261102.md has the starting point.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, a shared cloud host),
Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU (`zig build bench`).

## Method

Profiles: `perf record -e cpu-clock` (the host exposes no hardware
counters) over `bench-image serve` on one file or a whole operation's
inputs.

Each change is an interleaved A/B (`webp-perf-20261102/tools/ab.sh`): two
`bench-image` builds, before (A) and after (B), time every input of an
operation back to back, pinned with `taskset` to the last core, the order
alternating from input to input and round to round, 8 rounds of 60 ms
samples. `benchstat` compares the two (`benchstat.txt` in each change's
directory, with the raw `a.txt` and `b.txt`). The host's noise is large
(±10–50% between rounds on a row), but it moves A and B together, so the
headline is each row's median paired ratio, B's time over A's in the same
round, and their geomean by size class (`tools/paired.py`, `paired.txt`):
icons up to 64×64, up to 1 MP, and over 1 MP. An A/A run of the same build
gives 0.995–0.997, so a class geomean outside about ±1% is a change. Every B
build's output checksums the same as A's on every row (`bench-image check`).

## Lossless

Profile of `webp-decode-lossless`, every input for 300 ms each, before any
change: the pixel loop (`lossless.decode`, which inlines `Stream.pixels`)
53%, `Stream.rowDone` (the inverse transforms) 27%, prefix table building
12%, the rest under 3% each. On the maze screenshot, the worst row (0.54×
libwebp), the pixel loop is 48% (most of it backward reference copies,
moved one pixel at a time) and `rowDone` 42%, nearly all of that the
subtract green transform, which compiled to a scalar loop.

### Subtract green, eight pixels at a time

`addGreen` adds green to red and blue with `@Vector(8, u32)`
(`webp-perf-20261102/l2-subtract-green/`):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.019×    |
| to 1 MP     | 23   | 1.118×    |
| over 1 MP   | 7    | 1.102×    |
| all         | 43   | 1.084×    |

The maze screenshot gains 1.57×, the 600×600 pngimg 1.43×.

### Backward reference copies (not kept)

Moving copies whose source is behind them in blocks of eight
(`@Vector(8, u32)` loads and stores; a splat for a distance of 1) gained
1.2–1.25× on the pngimg and the QOI logo and 2–3% to 1 MP, but cost 4–6%
on icons in three variants (out of line, inline, only for copies of 16
pixels or more), and lost overall: the pixel loop's code around the copy
got worse for the short copies that icons and photos make. Kept aside for
the pixel loop rework below.

### One pixel loop per stream shape

The block copies above cost icons and photos because the pixel loop is
short of registers: with any more code in the copy, LLVM spilled the bit
buffer to the stack after every symbol (`mov %r8,-0x38(%rbp)` after each
`shrx` in the photo's hottest block), and a fill for distance 1 alone cost
the photos 5–12% (`webp-perf-20261102/l5-block-copies/v1-fill-only/`).
The loop is now instantiated at comptime for each shape of stream: with or
without a color cache, with or without an entropy image, and the ALPH
streams that may read past their end, so each copy holds only the state it
uses; and it no longer keeps a count of the pixels decoded, which the copy
computes from the row and column (`webp-perf-20261102/l4-loop-shapes/`,
6 rounds):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.040×    |
| to 1 MP     | 23   | 1.017×    |
| over 1 MP   | 7    | 1.016×    |
| all         | 43   | 1.024×    |

### Backward reference copies in blocks

On that loop, the copies come back: a distance of 1 is a fill, and a
distance of 8 or more moves blocks of eight pixels, each of whose source is
written before it is read; shorter distances stay one pixel at a time
(`webp-perf-20261102/l5-block-copies/`, 6 rounds against the loop shapes):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 0.994×    |
| to 1 MP     | 23   | 1.054×    |
| over 1 MP   | 7    | 1.023×    |
| all         | 43   | 1.031×    |

The pngimg 1.41×, the QOI logo 1.34×, the maze 1.27×, 3dbrick2 1.11×;
icons within noise. The 50 MP mosaic 1.021× (`l5-block-copies/large/`, 3
rounds) and the animations 1.017× (`l5-block-copies/anim/`, 8 rounds, the
two steps together against the build before them).

### Prefix tables without scanning the alphabet

Building a code's table counted its lengths one at a time into one
histogram, so each increment of the zeros' count waited on the last: 58% of
`build`, which was 21% of a 64×64 icon's decode. Now `build` skips eight
zero lengths at a time and counts the rest into four histograms, and a
simple code (one or two symbols, which red, blue, and alpha mostly are)
gets its one- or two-entry table directly, without `build`
(`webp-perf-20261102/l3-prefix-tables/`; tables checked equal to the old
`build`'s on 200,000 random length sets):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.260×    |
| to 1 MP     | 23   | 1.007×    |
| over 1 MP   | 7    | 1.004×    |
| all         | 43   | 1.077×    |

A first version summed the counts in a loop that LLVM vectorized into four
512-bit (zmm) instructions, and lost 5–16% on the 1 MP rows that ran after
it while gaining on icons, with the pixel loop and the transforms unchanged
byte for byte: on this Ice Lake server (model 106), 512-bit instructions
lower the core's clock for a while after them. Without the zmm sum, nothing
regresses. The lossy path has zmm in `LossyOut.row`, `vp8.decodeFrame`, and
`yuv.row` (16-lane `i32` vectors); see Lossy.

## Lossy

Profile of `webp-decode-lossy`, every input but the mosaic for 300 ms each,
by source line (`perf report --sort srcline`): the boolean decoder's `read`
38%, the rest of `coeffs` (the token loop) 8%, the ALPH chunks' lossless
pixel loop 5%, chroma upsampling 4%, the inverse DCT, YUV-to-RGB, intra
prediction, and the loop filter 1–3% each. The 16-lane loop filter is
already vector code; the token reader is the cost.

### No 512-bit vectors

`yuv.toRgbVec` computed 16 pixels in 32-bit lanes, a 512-bit vector, and
LLVM also widened the 16-pixel TrueMotion prediction and the DC sums to
512 bits: 155 zmm instructions in the lossy path, run every row. An
experiment built the same source without AVX-512 (`-Dcpu=native-avx512f`)
and was 3–5% faster in every class
(`webp-perf-20261102/y0-no-avx512-experiment/`). The change keeps AVX-512
but leaves the lossy path with no zmm instruction
(`webp-perf-20261102/y1-no-zmm/`):

- YUV to RGB in 16-bit lanes: each `(c * k) >> 8` is the high half of
  `(c << 8) * k` (`vpmulhuw`); red and green fit in `i16`, blue in `u16`
  with a saturating subtract, since its clip makes any negative 0. Checked
  equal to the scalar `toRgb` on all 2^24 (y, u, v).
- The RGBA interleave pairs bytes inside 16-bit lanes and interleaves the
  pairs per half (two 256-bit shuffles), and the upsampler stores each
  chroma pair as one little-endian 16-bit lane, with no shuffle across
  lanes, which LLVM had joined into 512 bits.
- TrueMotion prediction in `i16` lanes, and the DC sums as `u16` vector
  reductions.

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.068×    |
| to 1 MP     | 23   | 1.122×    |
| over 1 MP   | 7    | 1.091×    |
| all         | 43   | 1.100×    |

More than the no-AVX-512 experiment: the 16-bit conversion does half the
work of the 32-bit one, on top of the clock. A first try that kept the
32-bit math in two 8-lane halves got no gain: LLVM joined the halves back
into zmm, and narrowing to bytes before the interleave compiled to byte
inserts and extracts (2.1× the time in `yuv.row`).

### The token reader's bit as a branch

`Hot.read`, the boolean decoder in the token loop, compiled its two
outcomes to conditional moves, so every bit waited on the comparison that
decides it. A branch hint on the rarer outcome makes it a branch, which the
predictor mostly gets right on a token's skewed bits
(`webp-perf-20261102/y2-bool-branch/`, 6 rounds):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.051×    |
| to 1 MP     | 23   | 1.019×    |
| over 1 MP   | 7    | 1.004×    |
| all         | 43   | 1.026×    |

### Renormalizing in each arm of the bit

`Hot.read` set the bit and the range in its two arms, then renormalized
once after them, so the token loop tested the bit a second time after the
join (`setb`, then `test` and a branch). Renormalizing in each arm and
returning a constant lets LLVM fold the caller's test into the read's own
branch; the range is passed to `renorm` whole, not less one, which also
drops an increment from the chain from one bit to the next
(`webp-perf-20261102/y3-renorm-arms/`, 5 rounds):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.036×    |
| to 1 MP     | 23   | 1.038×    |
| over 1 MP   | 7    | 1.044×    |
| all         | 43   | 1.038×    |

The same shape in `Bool.read`, which reads the modes and headers, on top of
that (`y3-renorm-arms/bool/`, 5 rounds): icons 1.001×, to 1 MP 1.012×, over
1 MP 1.011×, all 1.009×. Both are in one commit.

### Clearing all coefficient blocks

After reconstruction the decoder cleared each of the 24 blocks whose code
said it had coefficients, a branch per block on data (1.7% of samples on
`photo_wikipedia-002`). Clearing all 768 bytes whenever the macroblock has
any coefficients is 24 stores of 256 bits, with no zmm
(`webp-perf-20261102/y4-clear-coef/`, 5 rounds):

| class       | rows | B speedup |
| ----------- | ---- | --------- |
| icons ≤ 64² | 13   | 1.007×    |
| to 1 MP     | 23   | 1.010×    |
| over 1 MP   | 7    | 1.016×    |
| all         | 43   | 1.010×    |

Tried and not kept: the token position as `usize` instead of `u5`, which
LLVM masks and spills each step: 1.002× over all, noise.
