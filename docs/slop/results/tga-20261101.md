# TGA decode and encode, 2026-11-01

`image.tga.Decoder` against Wuffs (the bar: Wuffs reads TGA), stb_image, and
Rust's `image`; `image.tga.encode` against stb_image_write and Rust's
`image`. Throughput is megapixels per second; a ratio is this package's
throughput over the arm's (above 1, ours is faster), the geometric mean over
a size class's rows of each row's median paired ratio over 10 rounds.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native`, Rust `target-cpu=native`. Each arm runs pinned to the last
core. Measured on main at 0d5385a (`convert` with Wuffs's rounding) plus
this branch. Raw output in `tga-20261101/bench-compare/` (`config.txt`,
`rss.txt`, `benchstat.txt`, `summary.txt`, `rows.txt`, every sample in
`raw-<arm>.txt`, and `rss-by-class.txt` with the script that made it).

Inputs: the 44 sources of `bench/corpus-gen/` (16×16 icons to the
50-megapixel photo mosaic) as ImageMagick writes them, 24-bit or 32-bit
true color with a top-left origin, uncompressed (`tga/none`) and RLE
(`tga/rle`); the encoder rows take the same pixels as RGB or RGBA
(`tga/rgba`). Size classes: icons (at most 4096 pixels, 13 rows), up to a
megapixel (23), larger (8).

## Decode

`tga-decode` and `tga-decode-rle` write RGBA; `tga-decode-bgra` writes BGRA,
the file's own order, which only Wuffs also offers. Every arm's output hashes
the same as ours on every row.

| operation, class | image MP/s | vs Wuffs | vs stb_image | vs image-rs | slowest row vs Wuffs      |
| ---------------- | ---------- | -------- | ------------ | ----------- | ------------------------- |
| decode, icons    | 2912       | 1.68     | 2.78         | 7.07        | 1.46, 16×16               |
| decode, ≤1 MP    | 4306       | 1.14     | 2.86         | 11.93       | 0.90, 447×1192 RGBA       |
| decode, >1 MP    | 2532       | 1.00     | 2.48         | 7.37        | 0.71, the 50 MP mosaic    |
| RLE, icons       | 1001       | 2.57     | 4.64         | 3.63        | 1.04                      |
| RLE, ≤1 MP       | 1707       | 4.45     | 6.37         | 7.36        | 1.14                      |
| RLE, >1 MP       | 1181       | 3.85     | 5.11         | 5.18        | 1.86                      |
| BGRA, icons      | 3069       | 1.49     | -            | -           | 1.40                      |
| BGRA, ≤1 MP      | 4674       | 1.06     | -            | -           | 0.99                      |
| BGRA, >1 MP      | 2762       | 1.00     | -            | -           | 0.97 (interval 0.91–1.13) |

Behind Wuffs: the 32-bit files at about a megapixel decoded to RGBA (0.90 to
0.96: a BGRA-to-RGBA swizzle per row), and the 50 MP RGB mosaic to RGBA,
0.71 (1394 against 1932 MP/s). The same file to BGRA ties Wuffs (0.985,
1621 against 1636), and both destinations use the same `convert` kernel
(`Expand3`, a 16-byte shuffle per four pixels) with only the mask changed,
so the gap is not the kernel's work. Wuffs is itself 18% faster to RGBA than
to BGRA on that one file. It is not explained yet; the next thing to try is
converting several rows per `Converter` call and checking how the 200 MB
output streams. The 24-bit photos up to 1.4 MP are 11–18% ahead of Wuffs.

RLE decode is 2.6–4.5× Wuffs: a run packet fills its span once, and raw
packets copy straight into the span buffer.

During development, uncompressed rows that fit in the reader's buffer
started converting straight from it instead of being copied out first:
16×16 icons went from 852 to 1288 MP/s (`bench-image bench`, 100 ms samples,
unpinned, so indicative only).

### Comparing pixels as integers in RLE encode

`packRow` asks whether two pixels are equal for every pixel it scans. With
`std.mem.eql` on the 3-byte pixels of a 24-bit image, the compiler compared
them a byte at a time. Comparing each pixel as one `u24` (or `u8` or `u32`)
integer made RLE encode 14% faster over every row. The A/B was interleaved
(8 rounds, old and new alternating first), pinned with `taskset -c 3`,
`bench-image bench tga-encode-rle` with 100 ms samples, compared with
benchstat; raw output in `tga-20261101/rle-compare-ab/` (`old` is
`std.mem.eql`, `new` integer compares, `mixed` integer compares for 3-byte
pixels only, `noinline` the new code with `packRow` not inlined):

| row                  | old MP/s | new MP/s | change    |
| -------------------- | -------- | -------- | --------- |
| kodim01 768×512 RGB  | 394.6    | 486.0    | +23%      |
| wikipedia_008 RGB    | 178.8    | 514.2    | +188%     |
| 50 MP mosaic RGB     | 167.2    | 290.5    | +74%      |
| RGBA, 512×512 and up | -        | -        | −1 to +3% |
| 16–64 px RGBA icons  | 511–942  | 492–905  | −4 to −8% |
| geomean, 44 rows     | 537.2    | 613.2    | +14.1%    |

The icons lose 4–8%, and they are RGBA, where `std.mem.eql` on 4 bytes was
already one compare. `mixed`, whose RGBA path is the old source exactly,
loses the same 4–8% on the same icons, and `tga.encode` compiles to the same
size in `new` and `mixed`. So the loss is how the rest of the inlined encoder
compiles (register and stack-slot assignment changed throughout), not the
compare. Not inlining `packRow` was worse everywhere (geomean +9.7% over old,
icons −2 to −11%). We kept the integer compare: RLE icons still encode at
3.1× stb_image_write and 5.5× image-rs. Memory is unchanged.
