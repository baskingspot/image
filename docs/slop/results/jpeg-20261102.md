# JPEG decode against libjpeg-turbo, 2026-11-02

`image.jpeg.Decoder` (wave 2, stage 1: baseline and progressive Huffman,
8-bit) against libjpeg-turbo 3.2.0, the bar and the oracle, Wuffs, and
stb_image, Rust's `jpeg-decoder` (through `image`), `zune-jpeg`, and Go's
`image/jpeg`. Every arm decodes a whole file from memory per call into RGB8
(bench/ops.tsv: `jpeg-decode` for baseline 4:2:0, `jpeg-decode-progressive`,
and `jpeg-decode-444` for baseline 4:4:4). libjpeg-turbo (TurboJPEG, its
default islow IDCT and fancy upsampling, with SIMD) and Wuffs checksum the
same as this package on all 132 rows; stb, `jpeg-decoder`, zune, and Go
upsample or convert differently and differ on every row, so the operations
are marked `own`. Throughput is megapixels per second; a ratio is this
package's throughput over the arm's (above 1, ours is faster), the geometric
mean over rows of each row's median paired ratio over 10 rounds.
docs/slop/jpeg.md has the decoder's design.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host whose rows swing by ±10% between rounds, so only paired ratios are
steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native`, Rust `target-cpu=native`, Go `GOAMD64=v3`. Inputs:
`bench/corpus-gen/jpeg/`, 44 files per operation written by libjpeg-turbo's
cjpeg (quality 85 for baseline and progressive, 90 for 4:4:4) from the QOI
benchmark suite's icons, photos, screenshots, and textures, 16 and 32 pixel
icons, and the 50-megapixel mosaic (bench/corpus/jpeg.sh). Raw output in `jpeg-20261102/`:
`summary.txt`, `rows.txt`, `benchstat.txt`, `raw-*.txt`, `rss.txt`, and
`rss-by-class.txt`.

## What the speed comes from

The optimizations below were each measured as an interleaved A/B on one
core during development, against the previous step; those runs' scripts
and raw output were not kept, so this records what each does rather than
its number. The table above measures the result.

- **IDCT in 16-bit lanes, two blocks at once.** The full-size 8-bit IDCT
  runs two blocks per call, one in each 128-bit half, with every product
  pair a pmaddwd (inline assembly, `simd.zig`; from portable vectors LLVM
  splits the multiply-add back into 32-bit multiplies, which measured 1.5×
  slower). A block goes this way when its dequantized coefficients'
  magnitudes sum to at most 5,900, which keeps every intermediate within 16
  bits (`idct.zig` derives the bound); otherwise 32-bit vectors up to
  15,000, then 64-bit, as the reference computes. A block whose AC
  coefficients are all zero is filled from its DC.
- **YCbCr to RGB in 16-bit lanes.** R's and B's chroma terms are each one
  pmulhrsw with constants an exhaustive search found exact over all 256
  chroma values, and G's two terms one pmaddwd; a unit test checks every
  chroma pair against the 32-bit formula.
- **Huffman decoding in registers.** The block decoders copy the bit reader
  into a local whose address is never taken, and the refill's common case
  (eight bytes, no 0xFF) is inline; AC lookahead entries decode a short code
  and its magnitude bits in one lookup. A 9-bit lookahead beat 8 and 10.
- **Vector fancy upsampling** (h2v1 and h2v2 in 16 lanes).

Matching libjpeg-turbo bit for bit cost nothing against it: these are its
own algorithms, and its SIMD build, which the arm runs, is no faster than
ours at them (the table). So decision 2 stands with no trade to write up.
