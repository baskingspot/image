# PNG decode against Wuffs, libpng, and libspng, 2026-11-01

`image.png.Decoder` (wave 1) against Wuffs, the bar, libpng and libspng,
the reference libraries, and stb_image, Rust's `png` crate (through
`image`), `zune-png`, and Go's `image/png`. Every arm decodes a whole file
from memory per call into RGBA8 (`png-decode`, bench/ops.tsv), and every
arm's output checksums the same on all 52 rows. Throughput is megapixels
per second; a ratio is this package's throughput over the arm's (above 1,
ours is faster), the geometric mean over rows of each row's median paired
ratio over 10 rounds. docs/slop/png.md has the decoder's design.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host whose rows swing by ±10–35% between rounds, so only paired ratios are
steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native`, Rust `target-cpu=native`, Go `GOAMD64=v3`. Inputs:
`bench/corpus-gen/png/`, 52 files: the QOI benchmark suite's icons,
photos, screenshots, and textures as their encoders wrote them, 16 and 32
pixel icons and the 50-megapixel mosaic as ImageMagick writes them, and a
Kodak photo and a 64-pixel icon as gray, palette, gray with alpha, and
Adam7 (bench/corpus/png.sh). Raw output in `png-20261101/`.

## Results

Two runs, the same code but for `compress`: the branch `image-png-inflate`
of baskingspot/compress (fd03d72, the inflate fast path, which this package
gets once the dependency is bumped), and v0.2.0, the dependency as pushed.

With `compress` at `image-png-inflate` (`png-20261101/compress-branch/`):

| icons ≤ 64² (17) | 64.3       | 0.76     | 1.38      | 1.25       | 0.80   | 0.72           | 0.66        | 2.49  |

So with the inflate branch we are 1.3–1.4× libpng and libspng in every size
class and 0.76–0.87× Wuffs; without it, 0.38× Wuffs and slower than libpng.
The slowest rows against Wuffs are the palette images (0.44× on the 64-pixel
icon, 0.59× on the Kodak photo; see the palette change below), the small
textures (0.57×), and photos (0.64× on kodim01), where Wuffs's inflate is
still 1.5× ours on literal-heavy data (`ab-inflate/`). We match or beat
Wuffs on gray (1.06×), gray with alpha (0.96×), interlaced (0.96×), and the
long screenshots (0.95×).

**Peak RSS** of one pass over all 52 inputs (GNU time): this package 239.3
MiB, libpng 239.9, libspng 239.7: the inputs and the 192 MiB RGBA mosaic,
nothing more. Wuffs 384.2 MiB: its work buffer holds the whole image's
filtered rows, 151 MB for the mosaic. stb 576.5, the `png` crate 578.7,
zune-png 431.3, Go 901.9. Our work memory is 72 KiB plus two rows: 72.1
KiB for a 16×16 icon, 76 KiB at 512×512 RGBA, 120 KiB for the 8192-wide
mosaic, and the same for every frame of an APNG.

## Where the time goes

`/tmp/prof` (not committed) timed a whole decode, `decodeConfig` alone, and
the same IDAT data through `zlib.Reader` alone, best of 5, on core 2. With
v0.2.0, inflate was 88% of a 16×16 icon, 74% of a 64×64 icon, 95–100% of
the Kodak photo, 93% of the amazon.com screenshot, 77% of the interlaced
photo, and 87% of the palette photo, at 77–260 MB/s. Config is 80–900 ns.
That made inflate the first target, in `compress` and not here.

## The changes measured

**Inflate** (baskingspot/compress, branch `image-png-inflate`, fd03d72; its
own write-up is compress's docs/slop/results/flate-fast-inflate-20261101.md).
A fast path through `flate.Reader`'s Huffman blocks, a 10-bit literal
table, and chunked match copies. On the IDAT data alone, interleaved, 7
rounds (`ab-inflate/`): 2.25× on kodim01, 2.93× on the mosaic, 2.65× on
amazon.com, 2.34× on a 512-pixel icon, 2.62× on a plant texture; now faster
than zlib everywhere and 0.67–1.10× Wuffs. End to end, this package's
`bench-image` built against v0.2.0 and against the branch, both with the
vector unfilter, 10 interleaved passes on one core, benchstat
(`ab-compress/`, `c020` against `cnew`): +113% geomean over the 52 rows,
every row p = 0.000, from +68% (512-pixel icon) to +159% (64-pixel icon).

**Unfiltering** (`src/png/filter.zig`). Sub, Average, and Paeth a pixel at a
time with the pixel's bytes as vector lanes, loaded and stored as an
integer of the pixel's width, the left pixel kept in a register, and Paeth
chosen with `@select`. On a 3 KiB row of random bytes (one core): Paeth 2.0×
(3-byte pixels) to 5.8× (8-byte), Sub 1.8× to 8.6×, Average up to 1.7× and
level at 3 bytes; 1-byte pixels gained nothing and stay scalar, and Average
on 2-byte pixels lost, so it stays scalar there. End to end, scalar against
vector, both on the inflate branch, 10 interleaved passes (`ab-unfilter/`,
`scalar2` against `cnew`): +13.8% geomean; +50% on the interlaced photo,
+37% on the gray-alpha photo and the RGBA test card, +18% on the mosaic;
the RGB photos within noise.

A first try loaded 3-byte pixels as `@Vector(3, u8)` and was slower than the
scalar loop for Sub and Average; padding to 4 lanes through arrays was
slower still, and a 4-byte load and store per 3-byte pixel stalled on store
forwarding. Moving pixels as `u24`/`u48` integers bitcast to 4 or 8 lanes
fixed all three.

**Palette to RGBA8.** Made after the two runs above: a palette image
decoded to RGBA8 now expands the palette's RGBA entries straight into the
destination row, where it went through RGB8 and a conversion, and each
entry is a 4- or 3-byte array copy rather than a `@memcpy` of a runtime
length. 8 interleaved passes, both on the inflate branch (`ab-palette/`,
`cnew` against `pal`): +48% on the palette icon, +44% on the palette photo,
and +28% and +39% on the two corpus files their encoders wrote as palettes;
the other rows run the same code and moved within noise (geomean −1.1%).
That takes the palette photo from 0.59× Wuffs to about 0.85×.

## Not yet done

- Inflate is still behind Wuffs on photos and textures (0.67× on the IDAT
  data alone). Wuffs decodes literals with a wider table and two literals'
  bits at a time; that is the next step in `compress`.
- Each row is copied out of inflate's window with `readSliceAll`; Wuffs
  inflates into its work buffer and unfilters in place. Decoding into the
  destination's rows directly would save a pass, but needs `compress` to
  inflate into a caller's buffer with the window kept behind it.
- Icons: a 16×16 decode is 8.5 µs against Wuffs's 7.5, mostly the dynamic
  Huffman header and table builds in `compress`.
