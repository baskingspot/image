# JPEG XL decode memory: aligned arrays and streamed VarDCT, 2026-11-02

Changes to `image.jxl.Decoder` on `wave4-jxl-mem`, each measured
against the build before it:

1. The work arena starts every array of 4096 bytes or more on a 64-byte
   cache line (`src/jxl/Arena.zig`), and `Config.work_len` grows by a 64th
   to cover the padding.
2. A large single-frame VarDCT image streams: it keeps a ring of three
   group rows of pixels instead of whole planes, and each group row is
   filtered and written to the caller's buffer once the row after it is
   in (docs/slop/jxl.md, Streaming).

Method: the `bench-image` binaries from `zig build bench -Doptimize=ReleaseFast`
of each build, run as `bench-image serve` side by side on the last core
(`taskset -c 3`), each row's loop sized once (`BENCHTIME_MS=50`), then 10
rounds alternating which build goes first per row, compared with benchstat
(median MP/s, p from a Mann-Whitney U test, n = 10). Peak RSS is GNU
time's maximum resident set of one `bench-image` pass over each size class's
inputs, as `just bench-compare` measures it: icons (up to 4096 pixels), to
1 MP, and over 1 MP. The bench maps `Config.work_len` without touching it,
so RSS counts the pages the decoder uses. Arena peaks and bounds per file
come from a ReleaseFast tool that decodes every frame and prints
`Arena.peak` and `work_len`. Operations and inputs: `jxl-decode` (44 files,
`cjxl -d 1`) and `jxl-decode-lossless` (44 files, `cjxl -d 0`) from
`bench/corpus-gen/jxl/`, RGBA16 out, first frame (bench/zig/jxl.zig).

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host), Linux 6.1, Zig 0.16.0. Base: origin/main 5a63f02.

Raw output in `jxl-mem-20261102/`: for each comparison (`align-lossy`,
`align-lossless`, `stream-lossy`, `stream-lossless`) the benchstat table,
each build's rows (`*-before.txt`, `*-after.txt`, benchstat's input), and
`*-rss.txt`; `peaks.txt` has every conformance, generated, and bench file's
arena peak and bound for main, main with change 1, and both changes, and
whether the last decodes every frame to the same f32 pixels as main.

## 1. Arrays on cache lines

The arena aligned an array only to its element (4 bytes for `f32`), so
the VarDCT planes started wherever the allocations before them ended. A
first A/B of streaming showed four 768×512 Kodak rows, which never
stream, 2–4% slower (p < 0.05, the rows varying between runs). The only
change on their path was `vardct.Shared` growing by 8 bytes, which moved
every later array, and the planes off a cache line. With both builds
aligning arrays of a page or more to 64 bytes, those rows were equal
(8 rows, 20 rounds: all non-streamed rows p > 0.5;
`align-found-benchstat.txt` and `align-confirm-benchstat.txt`).

| operation (rows)           | before MP/s | after MP/s | change | peak RSS before → after, MiB |
| -------------------------- | ----------- | ---------- | ------ | ---------------------------- |
| `jxl-decode` (44)          | 10.47       | 10.64      | +1.57% | 986.1 → 986.1                |
| `jxl-decode-lossless` (44) | 4.181       | 4.193      | +0.28% | 989.0 → 989.0                |

Geometric means of the rows' medians. On lossy rows, ten are faster at
p < 0.05 and none slower: the 50-megapixel mosaic +8.36% (15.43 → 16.71
MP/s), the two 1200×1200 photos +7.32% and +4.44%, wikipedia-001 +4.76%,
the apple.com screenshot +5.34%. No lossless row moves at p < 0.05.
Memory: at most 63 bytes per array of 4096 bytes or more; `work_len`
grows by a 64th to cover it (on the mosaic, 933.1 MB to 947.7 MB), and
the arena's peak by at most a few hundred bytes on any file in the
corpus (627,428,892 to 627,429,104 bytes on the mosaic). RSS by class is
unchanged to 0.1 MiB.

## 2. Streaming

Against change 1. Which bench files stream: those of five group rows or
more (over 1024 rows at the default group size, 256) without patches, splines, noise,
upsampling, or chroma subsampling. In the lossy set, the mosaic, the two
1200×1200 photos, plants-plant_02 (1024×1316), academy_awards (447×1192),
and the three tall web screenshots (1313 wide, 4755 to 6097 tall), the
last five with alpha. academy_awards is the only one under a megapixel:
under a megapixel, only an image narrower than about 1000 pixels is over
1024 rows tall (below five group rows a ring of three plus the window
saves nothing), so the to-1-MP class, whose peak is its largest
member's, does not move.

**Memory.** Peak RSS, MiB, as `just bench-compare` measures it:

| class               | before | after |
| ------------------- | ------ | ----- |
| lossy, icons        | 3.1    | 3.0   |
| lossy, to 1 MP      | 28.1   | 28.0  |
| lossy, over 1 MP    | 985.9  | 507.4 |
| lossless, icons     | 3.0    | 3.0   |
| lossless, to 1 MP   | 24.8   | 24.8  |
| lossless, over 1 MP | 989.0  | 989.0 |

The over-1-MP class is the mosaic: its RGBA16 output is 384 MiB, so what
the decoder holds beyond it falls from about 600 MiB to about 120 MiB.
libjxl's figure for the class in `jxl-20261102.md` is 527.0 MiB and
jxl-oxide's 1852.5. Arena peaks and work bounds (`peaks.txt`), MB:

| file                           | peak before | peak after | `work_len` before | after |
| ------------------------------ | ----------- | ---------- | ----------------- | ----- |
| mosaic 8192×6144               | 627.4       | 127.3      | 947.7             | 243.2 |
| amazon.com 1313×6097, alpha    | 133.8       | 53.9       | 333.4             | 333.4 |
| cnn.com 1313×5241, alpha       | 115.4       | 49.0       | 291.8             | 291.8 |
| apple.com 1313×4755, alpha     | 109.0       | 50.4       | 268.1             | 268.1 |
| plant_02 1024×1316, alpha      | 28.6        | 25.3       | 86.5              | 86.5  |
| academy_awards 447×1192, alpha | 11.1        | 10.3       | 55.7              | 55.7  |
| tecnick 1200×1200              | 24.3        | 22.1       | 67.5              | 59.5  |

With alpha the bound stays: cjxl palettes a two-level alpha over the
whole frame, its transforms are undone only on the whole frame, and they
are not known until the frame is read, so the bound keeps whole planes;
the planes are taken once they are known, so the peak falls anyway. A
caller that maps work memory gains the peak's fall; one that fills it
gains the bound's.

**Speed.** `jxl-decode` geomean 10.68 → 10.67 MP/s (−0.06%), no row
slower at p < 0.05 (two 16×16 icons faster by 1–2%); `jxl-decode-lossless`
4.198 → 4.194 (−0.10%), no row at p < 0.05. The streamed rows: mosaic
16.80 → 16.76, amazon.com 13.00 → 13.05, tecnick-001 17.39 → 16.88
(p = 0.105), plant_02 8.325 → 8.315. Streaming does more work, a copy of
each group row and its margins into the window and the filters run over
16 more rows per group row (6% at 256), and in the 20-round check of
section 1 the two smallest streamed images paid for it: tecnick-001
−2.09% (p = 0.015) and plant_02 −1.78% (p < 0.001)
(`align-confirm-benchstat.txt`). On the mosaic and the screenshots it is
within noise.

**Trade.** For images of five group rows or more, about a 2% loss at the
smallest against an arena peak 7–80% lower, and on the 50-megapixel
photograph about half the process's peak RSS (below libjxl's), at no
measurable speed cost. Smaller images are unchanged.

The measured build took the ring when the frame began; taking it at the
end of LfGlobal, which brought the bound with alpha back down from whole
planes plus the ring, moves those allocations and nothing in a hot loop,
and was not re-timed.
