# JPEG XL decode memory: aligned arrays and streamed VarDCT, 2026-11-02

Changes to `image.jxl.Decoder` on `wave4-jxl-mem`, each measured
against the build before it:

1. The work arena starts every array of 4096 bytes or more on a 64-byte
   cache line (`src/jxl/Arena.zig`), and `Config.work_len` grows by a 64th
   to cover the padding.

Method: the `bench-image` binaries from `zig build bench -Doptimize=ReleaseFast`
of each build, run as `bench-image serve` side by side on the last core
(`taskset -c 3`), each row's loop sized once (`BENCHTIME_MS=50`), then 10
rounds alternating which build goes first per row, compared with benchstat
(median MP/s, p from a Mann-Whitney U test, n = 10). Peak RSS is GNU
time's maximum resident set of one `bench-image` pass over each size class's
inputs, as `just bench-compare` measures it: icons (up to 4096 pixels), to
1 MP, and over 1 MP. The bench maps `Config.work_len` without touching it,
so RSS counts the pages the decoder uses. Arena peaks and bounds per file
come from a ReleaseFast tool that decodes every frame and prints
`Arena.peak` and `work_len`. Operations and inputs: `jxl-decode` (44 files,
`cjxl -d 1`) and `jxl-decode-lossless` (44 files, `cjxl -d 0`) from
`bench/corpus-gen/jxl/`, RGBA16 out, first frame (bench/zig/jxl.zig).

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host), Linux 6.1, Zig 0.16.0. Base: origin/main 5a63f02.

Raw output in `jxl-mem-20261102/`: for each comparison (`align-lossy`,
`align-lossless`) the benchstat table, each build's rows (`*-before.txt`,
`*-after.txt`, benchstat's input), and `*-rss.txt`.

## 1. Arrays on cache lines

The arena aligned an array only to its element (4 bytes for `f32`), so
the VarDCT planes started wherever the allocations before them ended. A
first A/B of streaming showed four 768×512 Kodak rows, which never
stream, 2–4% slower (p < 0.05, the rows varying between runs). The only
change on their path was `vardct.Shared` growing by 8 bytes, which moved
every later array, and the planes off a cache line. With both builds
aligning arrays of a page or more to 64 bytes, those rows were equal
(8 rows, 20 rounds: all non-streamed rows p > 0.5;
`align-found-benchstat.txt` and `align-confirm-benchstat.txt`).

| operation (rows)           | before MP/s | after MP/s | change | peak RSS before → after, MiB |
| -------------------------- | ----------- | ---------- | ------ | ---------------------------- |
| `jxl-decode` (44)          | 10.47       | 10.64      | +1.57% | 986.1 → 986.1                |
| `jxl-decode-lossless` (44) | 4.181       | 4.193      | +0.28% | 989.0 → 989.0                |

Geometric means of the rows' medians. On lossy rows, ten are faster at
p < 0.05 and none slower: the 50-megapixel mosaic +8.36% (15.43 → 16.71
MP/s), the two 1200×1200 photos +7.32% and +4.44%, wikipedia-001 +4.76%,
the apple.com screenshot +5.34%. No lossless row moves at p < 0.05.
Memory: at most 63 bytes per array of 4096 bytes or more; `work_len`
grows by a 64th to cover it (on the mosaic, 933.1 MB to 947.7 MB), and
the arena's peak by at most a few hundred bytes on any file in the
corpus (627,428,892 to 627,429,104 bytes on the mosaic). RSS by class is
unchanged to 0.1 MiB.
