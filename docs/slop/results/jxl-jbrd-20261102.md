# JPEG XL JPEG reconstruction against libjxl, 2026-11-02

`image.jxl.JpegReconstructor` (stage 2: the `jbrd` box and the
coefficients from `Decoder.decodeJpeg`) against libjxl 0.12.0, the bar and
the oracle. Both arms rebuild the original JPEG from a JPEG XL file in
memory per call into the caller's buffer, on one thread, with no pixels
(bench/ops.tsv: `jxl-jbrd` for baseline sources, `jxl-jbrd-progressive`
for progressive ones). libjxl runs `JxlDecoder` with no parallel runner,
subscribed to `JXL_DEC_JPEG_RECONSTRUCTION`, as djxl does for a .jpg
output (bench/c/libjxl-jbrd.c); ours keeps its work memory between calls
(bench/zig/jxl_jbrd.zig). Both arms checksum the same on all 88 rows: the
output is the same JPEG, byte for byte. Throughput is megapixels per
second of the image; a ratio is this package's throughput over libjxl's
(above 1, ours is faster), the geometric mean over rows of each row's
median paired ratio over 10 rounds.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arm `cc -O3
-march=native`. Inputs: `bench/corpus-gen/jxl_jbrd/`, 44 files per
operation: the JPEG rows' sources (the QOI benchmark suite's icons, photos,
screenshots, and textures, 16 and 32 pixel icons, and the 50-megapixel
mosaic) written by cjpeg at quality 85, baseline or progressive, then
transcoded by `cjxl --lossless_jpeg=1 --num_threads=0`
(bench/corpus/jxl_jbrd.sh). Command: `just bench-compare 10 jxl-jbrd
jxl-jbrd-progressive`. Raw output in `jxl-jbrd-20261102/`: `summary.txt`,
`rows.txt`, `benchstat.txt`, `raw-*.txt`, `rss.txt`, and `config.txt`.

## Results

| operation, rows (count)    | image MP/s | vs libjxl |
| -------------------------- | ---------- | --------- |
| baseline, icons (13)       | 13.6       | 1.48      |
| baseline, to 1 MP (23)     | 32.6       | 0.33      |
| baseline, over 1 MP (8)    | 33.4       | 0.31      |
| progressive, icons (13)    | 12.3       | 1.67      |
| progressive, to 1 MP (23)  | 26.1       | 0.57      |
| progressive, over 1 MP (8) | 26.8       | 0.56      |
| all (88)                   | 23.1       | 0.63      |

We win on icons (a 16×16 icon takes about 39 µs against libjxl's 98) and
lose past them: a third of libjxl's speed on baseline sources and a bit
over half on progressive ones. On the 50-megapixel mosaic we rebuild at
33.3 MP/s against libjxl's 99.1 (0.33×) baseline, and 26.6 against 45.5
(0.58×) progressive.

Where the time goes, from a scratch driver that times a whole `run`
against `Decoder.decodeJpeg` alone on the same file, 20 calls each,
pinned to one core:

| file                      | run      | decodeJpeg | share |
| ------------------------- | -------- | ---------- | ----- |
| 16×16 icon, baseline      | 46 µs    | 22 µs      | 49%   |
| 343×480 screenshot        | 3.85 ms  | 3.38 ms    | 87%   |
| 1200×1200 photo, baseline | 40.4 ms  | 32.0 ms    | 79%   |
| 1200×1200 photo, prog.    | 46.7 ms  | 32.1 ms    | 68%   |
| 1313×4755 page, baseline  | 172.6 ms | 145.9 ms   | 84%   |
| 1313×4755 page, prog.     | 213.9 ms | 136.1 ms   | 63%   |

The coefficient pass in the JPEG XL decoder takes two thirds to seven
eighths of the time past icons. On the baseline photo it alone takes 32
ms, where libjxl's whole reconstruction takes about 12.5 ms (0.31× of our
40.4). The `jbrd` side (the box, the Brotli payload, and the JPEG writer)
is the rest: about 8 ms baseline and 15 ms progressive on that photo, 180
and 100 MP/s. The writer is not the first place to spend effort; the
coefficient pass, which is the JPEG XL orb's, is.

**Peak RSS** (GNU time, one pass over each size class's inputs: the inputs
and output buffers every arm holds alike, plus the library's own memory),
MiB:

| operation, class       | image | libjxl |
| ---------------------- | ----- | ------ |
| baseline, icons        | 3.0   | 8.2    |
| baseline, to 1 MP      | 14.9  | 19.6   |
| baseline, over 1 MP    | 546.9 | 558.0  |
| progressive, icons     | 3.0   | 8.2    |
| progressive, to 1 MP   | 14.9  | 19.5   |
| progressive, over 1 MP | 546.9 | 554.5  |

We use less memory in every class. The large class is the mosaic: both
arms hold its coefficients, 64 i16 per block of each component (about
300 MiB for 50 megapixels at 4:4:4 and 150 MiB at 4:2:0); ours sit in the
caller's work memory, sized by `Jpeg.maxCoefs` for 4:4:4 whatever the
sampling. `Decoder.jpegWorkLen` asks for about 9.8 MB even for a 16×16
file, but untouched pages cost nothing, so the icons' 3 MiB is the real
use; a caller that touches the whole buffer pays the 9.8 MB.
