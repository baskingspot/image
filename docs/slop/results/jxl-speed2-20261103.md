# JPEG XL decode speed, pass 2: setup and the coefficient loop, 2026-11-03

Changes to `image.jxl.Decoder` on `wave4-jxl-speed2`, after
`jxl-speed-20261103.md`, each measured against the build before it. They
came from profiling `bench-image serve` with `perf record` on a 16×16 icon
and the 1200×1200 photo:

1. **The coefficient loop, specialized on the code's kind.** VarDCT's
   coefficient loop (`vardct.decodeBlock`) read each symbol through code
   that tested, per symbol, whether the code is prefix or ANS and whether
   LZ77 is on. `entropy.Reader.Kind` names the four combinations, and
   `readPassGroup` picks one copy of the loop per pass group
   (`switch (kind) inline else`), which reads through
   `Reader.readClusterAs` with both tests fixed at compile time.
2. **The default dequantization tables, kept in the binary.** Each frame
   computed the multipliers of every table its strategies use from the
   tables' parameters (`quant.multipliers`), about 17% of a 16×16 lossy
   icon's time, most of it in `std.math.pow`. `quant.read` now reports
   which tables are the defaults, and the defaults of tables 0 to 10 (DCT8
   to DCT32, 30 KiB of read-only data) are computed at compile time
   (`quant.defaultMultipliers`). A unit test checks them bit for bit
   against the run-time computation. The larger tables (DCT64 and up, up to
   768 KiB more) are still computed when a frame uses them.
3. **The VarDCT planes, no longer cleared.** `Shared.allocPlanes` zeroed
   all three planes (or a streamed frame's ring of three group rows) before
   decoding, 4.3% of the 1200×1200 photo's time. Zig 0.16's
   `compiler_rt.memset` stores a byte at a time (plan.md, the memset item).
   Without chroma subsampling, every block has a strategy
   (`readPassGroup` refuses an unset one), and the last pass writes every
   pixel of each varblock in all three channels before anything reads
   them, so the planes are cleared only when a channel is subsampled. To
   check that, a build that filled the planes with NaN instead of leaving
   them as they were hashed the same as the build that cleared them on all
   547 frames of the 298 JPEG XL files in `corpus/` and
   `bench/corpus-gen/` (streamed and whole frames, upsampling, noise,
   patches, splines, progressive passes, and LF frames).

Rejected: **EPF's differences, shared between offsets.** Passes 0 and 1
compare each pixel's neighbourhood with the one at each offset, and the
offsets come in opposite pairs, so a ring of per-direction differences
(summed over the channels) can serve both offsets of a pair and all five
taps. On this corpus it measured −0.90% (icons −3%, everything else
unchanged): `cjxl -d 1` runs one EPF iteration, which is pass 1 with two
directions, and pass 0, where the sharing saves most, runs only at three.
It also reordered float sums (against libjxl on the 43 lossy files other
than the mosaic, samples one 16-bit step off went from 1,285,091 to
1,285,502, with no file's largest difference growing) and needed 120 more
bytes a column. Not kept.

Method: as in `jxl-speed-20261103.md`. `bench-image` from `zig build bench
-Doptimize=ReleaseFast` for each build, run as `bench-image serve` side by
side on the last core (`taskset -c 3`), each row's loop sized once
(`BENCHTIME_MS=50`), then 6 rounds alternating which build goes first per
row, compared with benchstat (median MP/s, p from a Mann-Whitney U test,
n = 6). Peak RSS is GNU time's maximum resident set of one pass over each
size class's inputs. Operations: `jxl-decode` (44 files, `cjxl -d 1`),
`jxl-jbrd` (44 files, `cjxl --lossless_jpeg=1` from cjpeg's baseline
JPEGs), and `jxl-decode-lossless` (44 files, `cjxl -d 0`), from
`bench/corpus-gen/`, RGBA16 out, first frame.

Machine: Intel Xeon Processor @ 2.60GHz (Ice Lake, 4 vCPUs, AVX-512, a
shared cloud host), Linux 6.1, Zig 0.16.0. Base: the build of
`wave4-jxl-speed` (its decoder is the same on main f2721b1).

Raw output in `jxl-speed2-20261103/`: for each comparison the benchstat
table, each build's rows (`*-before.txt`, `*-after.txt`), and `*-rss.txt`.
`c4-lossy` is the rejected EPF change, `c5-*` change 1, `c6-lossy` change
2, `c7-lossy` change 3, and `all-*` the base against the final build.

Geometric means of the rows' medians, MP/s; peak RSS of the whole
operation, MiB, before → after.

Base against final: 37 of 44 lossy rows faster at p = 0.002, and none
slower; 34 of 44 rebuilding JPEGs. Lossless is unchanged: no row moves
beyond 1% (one row −0.8%, p = 0.002), since it shares none of this code.

Notable rows, base against final. Lossy: 16×16 icons +23–31% (5.9 → 7.6
MP/s), 64×64 +14–34%, the 64×64 texture +55% (15.9 → 24.5), kodim01 +10%,
the 512×512 icons +4%, the 1200×1200 photos +6% and +4% (28.8 → 30.5), the
mosaic +3.6% (28.8 → 29.9), the cnn.com screenshot unchanged. Rebuilding
JPEGs (change 1 alone): 64×64 icons +4–7%, the photos +2%, the mosaic
+1.5%. Change 2 is fixed setup per frame, so it is largest on small
images; change 3 is per pixel, 1–3% at every size.

Peak RSS does not move beyond 0.7 MiB. Change 2 adds 30 KiB of read-only
data and allocates the default tables' multipliers no more.

The 1200×1200 photo now decodes lossy at 30.5 MP/s against libjxl's 37.7
in `jxl-20261102.md` on this machine (not re-run): 0.81×, from 0.76×.

## Pixels

Every change keeps the output bit for bit: each build checksums the same
on every row of every operation (`ab.sh` compares them before timing),
base against final included.
