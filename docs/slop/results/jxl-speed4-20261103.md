# JPEG XL decode speed, pass 4: nothing kept, 2026-11-03

Five changes to `image.jxl.Decoder`, tried after `jxl-speed3-20261103.md`
on the remaining profile (`perf record` of `bench-image serve` on the
1200×1200 photo). Every one kept the output bit for bit on every bench row,
and none measured faster than this host's noise, so none is kept. They are
written down so that they are not tried again on the same grounds.

The profile they came from, after pass 3. Lossy: `passGroup` 31%, of which
the coefficients' entropy decoding (`decodeBlock`) is 21% and their ANS
symbol reads 11%; the XYB to sRGB transform 13%; Modular (the LF and HF
metadata) 11%; EPF 10%; the IDCT (`toPixels`) 9%; Gaborish 9%; `memcpy`
4%. Lossless: one function, `decodeStream`, at 94%, with no instruction
over 4% of it: every channel of the photo walks its flattened tree (tens to a
few hundred splits) with the weighted predictor and no reference properties, at
about 160 cycles a sample.

1. **ANS without branches, and alias entries of eight bytes.** The
   symbol's half of its bucket (`pos >= cutoff`) and the renormalization
   (`state < 2^16`) were chosen with masks and selects instead of
   branches, and `entropy.Alias` shrank from ten bytes to eight (a bucket
   holds at most 128 slots and a symbol is below 256, so the cutoff and
   the right symbol fit a byte; the stored offset never wraps, since an
   over-full symbol keeps more than the under-full one's cutoff). Lossy
   −1.21%, lossless −0.53%. The eight-byte entries alone, with the
   branches back, were neutral in a quicker check (best of 25 serve runs
   of the photo: 712.5 against 715.9 ms).
2. **The weighted predictor's four errors side by side.** `Wp.pred_err`
   as one array of `@Vector(4, u32)` instead of four arrays, so the
   three neighbours' errors are three vector loads and the update two
   vector stores, and the four weights' sums one vector add. Lossless
   −0.50% (12 rounds).
3. **Gaborish and EPF's passes run a row apart.** Each pass already
   keeps a ring of the rows it overwrites, so the passes can follow each
   other down a band, each taking row `y` once the pass before has written
   row `y + r`; a pass never reads a row a later pass has written. The
   band's 3.7 MB then stays in cache between passes. Lossy +1.02%, the
   1200×1200 photos +2–3% at p > 0.3, best of rounds +1.5%. The bands fit
   this host's L3, so the passes were not waiting on memory; the rings
   would live together (18 rows of three planes instead of 7), which needs
   a new term in `workBound` and a fallback for frames wider than
   `frame_scale` canvases, too much for a gain inside the noise.
4. **The IDCT without its two copies, transposing by tiles.** `idct2d`'s
   first column pass read the stored coefficients in place and its last
   wrote the plane's rows, instead of copying through scratch, and the
   transpose between them went by 8×8 tiles of shuffles instead of a
   float at a time. Lossy −0.46% (15 rounds).
5. **AVX-512's sixteen lanes for the color transform and the filters.**
   `Xyb.applyTo`, Gaborish, and EPF (two blocks a vector, each lane with
   its block's sigma, a block below the minimum sigma keeping its pixels
   through a select) at `std.simd.suggestVectorLength(f32)` lanes, then
   eight, then one; a lane computes the same at either width. Lossy
   −1.00%, the mosaic −2.44% (p = 0.02): the 512-bit operations cost
   more than the halved count saves on this Ice Lake.

**The noise floor.** An A/A run (the same build as both arms, 6 rounds)
gave −0.20% on the medians' geometric mean and +2.0% on the best rounds'.
Changes under about 1.5% cannot be told apart on this host with 6 rounds,
and the longer runs (12 and 15 rounds) above did not move any change out
of that band.

Method: as in `jxl-speed2-20261103.md`: `bench-image serve` builds side by
side on the last core (`taskset -c 3`), loops sized once, rounds
alternating which build goes first per row, benchstat (median MP/s,
Mann-Whitney U), and GNU time's peak RSS per size class. "Best of rounds"
is the geometric mean over rows of each build's fastest round, since a
shared host's interference only slows a run. Operations: `jxl-decode` (44
files, `cjxl -d 1`) and `jxl-decode-lossless` (44 files, `cjxl -d 0`),
RGBA16 out. Every build checksums the same as main on every row.

Machine: Intel Xeon Processor @ 2.60GHz (Ice Lake, 4 vCPUs, AVX-512, a
shared cloud host), Linux 6.1, Zig 0.16.0. Base: main 47a9a68. Rows vary
by up to ±30% within a run.

Raw output in `jxl-speed4-20261103/`: `a-*` to `e-*` are changes 1 to 5,
and `aa-lossy` the A/A run. Change 3's and 4's base had change 2 in it,
which lossy decoding reaches only through its LF's Modular stream.

## What is left

Lossy decoding is about 0.86× libjxl on the 1200×1200 photo and lossless
about 0.97× (`jxl.md`, Measurements). What remains is spread thin: the
coefficient loop is a chain of dependent loads per coefficient (the
nonzero-count context, the context map, the alias entry), which branches
and table sizes do not shorten; the restoration filters are bound by their
arithmetic, not memory; and lossless runs the same algorithm as libjxl at
about the same speed. A change worth landing now likely needs a different
algorithm rather than tuning: the XYB transform's power function with
fewer operations (which moves some 16-bit samples by one step, so it needs
the oracle's lossy tolerance checked, not just the bench checksums), or
lossless trees of a single property (`cjxl -e 2` and `-e 3`) as tables,
which the default-effort bench files would not show.
