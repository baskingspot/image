# QOI decode: one table loop for every size, with RGBA on its own branch, 2026-11-02

`qoi-perf-20261102.md` left QOI decode with two loops: below 64×64 pixels
(`small`) a branch per chunk kind, and from 64×64 a 256-entry table for
DIFF, LUMA, RGB, and RGBA. The threshold came from single-file rows, which
time one file again and again, and the QOI orb suspected it was tuned to a
branch predictor that had memorized one tiny file. `icon-rotation-20261102.md`
then added rotating rows (`qoi-decode-icons`), which cycle through 64
distinct icons per size, and found that QOI icon numbers move when the file
changes from call to call: the rotating rows are the icon numbers to quote.

## Method

`ab.sh` (in the raw directory) is `just bench-compare`'s method with arms
given as binaries: checksums from every arm, peak RSS, then interleaved
rounds where each row's arms run back to back in an order that rotates,
pinned to core 3 with `taskset`, 50 ms a sample, compared with benchstat
and `bench/summary.awk`. Every arm's checksums match on every row.

CPU: Intel Xeon Processor @ 2.60GHz (3.3 GHz under load), 4 vCPUs,
AVX-512, a shared cloud host; Linux 6.1, Zig 0.16.0 ReleaseFast for this
CPU, C arms `cc -O3 -march=native`, Rust `target-cpu=native`. `before` is
origin/main's decoder (0d94f97; `src/qoi/` is unchanged since 9caf0db).

Steps, each in its own raw directory:

1. `threshold/`: the rotating rows alone, 30 rounds, with `small` at 64×64
   (main), 32×32, and 0 (the table loop for every image), and the `qoi`
   crate and Wuffs.
2. `table/`: `small = 0` against main on every QOI decode row, 10 rounds.
3. `rgba/`: the table loop with an RGBA branch (`variant-rgba.diff`)
   against `small = 0` and main, on icons, testcard, 3dbrick2, kodim01,
   and wikipedia-002, 10 rounds.
4. `rgb/`: that loop with RGB (0xfe) on the branch too (`variant-rgb.diff`)
   against it, same rows.
5. `ab/`: the change against main on all 91 QOI decode rows with every arm,
   10 rounds.

## What the rotating rows show

With 30 rounds (`threshold/benchstat.txt`, MP/s, ±1–3%):

| rotating row | small = 64×64 (main) |          32×32 | 0 (table only) | `qoi` crate | Wuffs |
| ------------ | -------------------: | -------------: | -------------: | ----------: | ----: |
| 16×16        |                253.1 |      248.5 (~) | 311.3 (+23.0%) |       274.9 | 146.2 |
| 32×32        |                248.3 | 280.4 (+12.9%) | 282.2 (+13.7%) |       225.3 | 162.4 |
| 64×64        |                317.8 |      318.7 (~) |      318.7 (~) |       258.6 | 197.0 |

So the branch per kind loses wherever the file changes between calls; it
wins only on single-file rows, where the predictor has learned the file:
`small = 0` ran the single-file 16×16 and 32×32 icons 1.25–2.25× slower
than main (`table/benchstat.txt`).

Why the table loop is slow there even when every branch is predicted: an
RGBA chunk's pixel is the four bytes that follow, but through the table it
is `addBytes((px & keep) | (next & ~keep), delta)` with `keep = 0` and
`delta = 0`, so it waits on the pixel before it, about five dependent
operations. In the branch-per-kind loop an RGBA pixel depends on nothing.
Icons with alpha are full of RGBA chunks (every change of alpha at an
antialiased edge is one); opaque images have none.

So RGBA gets its own branch in the table loop, as INDEX and runs already
do (`variant-rgba.diff`), and the branch-per-kind loop goes. On the rows
of step 3 (`rgba/benchstat.txt`), against `small = 0`: rotating 16×16
+37%, 32×32 +13%, 64×64 +5%; single-file icons +14–34%; kodim01,
wikipedia-002, 3dbrick2, and testcard +1–11%. Taking RGB (0xfe) on the
same branch too (step 4) gained 12% on testcard and 3–9% on the
single-file 64×64 icons but lost 5–7% on the rotating rows and 8–10% on
kodim01 and wikipedia-002, whose RGB chunks are frequent and
unpredictable, so it is not taken.

## Results

The change against main (`ab/summary.txt`; main against the same arms in
`ab/summary-before.txt`), geometric means by size class:

| ------------------ | ---------: | ------: | ----------- | ----------- | -------------- | ----------- |
| rotating icons     |      362.3 |    1.32 | 1.62 → 2.15 | 1.39 → 1.82 | 1.08 → 1.42    | 3.07        |
| icons, single file |      438.8 |    0.89 | 1.88 → 1.67 | 1.44 → 1.27 | 0.97 → 0.87    | 3.28        |
| ≤ 1 MP             |      527.6 |    1.05 | 1.82 → 1.92 | 1.77 → 1.87 | 1.11 → 1.17    | 2.87        |
| > 1 MP             |      329.6 |    1.02 | 1.63 → 1.67 | 1.59 → 1.63 | 1.14 → 1.17    | 2.31        |
| BGRA, icons        |      365.4 |    0.92 | 1.50 → 1.38 | -           | -              | -           |
| BGRA, ≤ 1 MP       |      459.0 |    1.05 | 1.58 → 1.66 | -           | -              | -           |
| BGRA, > 1 MP       |      308.7 |    1.03 | 1.51 → 1.55 | -           | -              | -           |
| all 91 rows        |      425.6 |    1.01 | 1.67 → 1.68 |             |                |             |

The rotating rows by size (`ab/rows.txt`): 16×16 446.1 MP/s against
255.8 (1.75×), 32×32 312.8 against 252.3 (1.24×), 64×64 340.7 against
315.5 (1.07×); against the `qoi` crate 1.60, 1.38, and 1.31, where main
was 0.94, 1.11, and 1.21.

The trade: the single-file 16×16 and 32×32 icon rows, which main decoded
with the branch per kind, are 0.66–0.97× main (0.66–0.96 to RGBA, 0.74–0.97
to BGRA), and against the `qoi` crate the single-file icon class falls from
0.97 to 0.87. Those rows measure a file the predictor has learned; the
rotating rows on the same sizes are 1.24–1.75× faster. The single-file
64×64 icons gain 12–28%, the 512×512 icons 7–11%, and the textures up to
16%. Of the larger rows, testcard_rgba to BGRA is 0.93× (run-heavy; its
loop is main's apart from the RGBA branch), and 3dbrick2 is 1.02–1.04×.

Peak RSS is unchanged (`ab/rss.txt`): 257.7 MiB on `qoi-decode`, 2.7 MiB
against 2.6 on the rotating rows. The decoder's state is the same, and the
code is smaller: one loop instead of two.
