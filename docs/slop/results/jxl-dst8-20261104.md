# JPEG XL decode: 8-bit destinations packed directly, 2026-11-04

A change to `image.jxl.Decoder`'s output on `wave4-jxl-dst8`, the last
item of `jxl.md`'s speed list that needs no tolerance recheck. It keeps
the output bit for bit.

A lossy frame's native format is 16-bit (`rgb16`, `rgba16`, their
premultiplied and grey forms), so an 8-bit destination took two steps per
chunk of 256 pixels: `packPivot` quantized the float planes to the 16-bit
pivot in a stack buffer, then the shared converter narrowed each sample to
its high byte (`c >> 8`, the package's 16-to-8 rule) into the destination.

**The change.** `packsDirect` also accepts an 8-bit destination with the
16-bit pivot's channels (`narrowed(p)`), or those with an opaque alpha
added (rgb16 to `rgba8` or `rgba8_premul`, gray16 to `gray_alpha8` or
`gray_alpha8_premul`), and `packPivot` then writes the destination itself:
it quantizes to 16 bits as before and stores each sample's high byte,
eight pixels at a time. Converting keeps premultiplied samples
premultiplied and straight ones straight, so narrowing is the same shift
for both. Other destinations (`bgra8`, 16-bit to grey or colour, floats)
still go through the converter.

## Results

Geometric means of the rows' medians, MP/s; peak RSS of the whole
operation, MiB, before → after.

| run | operation (rows)             | before | after | change | peak RSS      |
| --- | ---------------------------- | ------ | ----- | ------ | ------------- |
| 1   | `jxl-decode`, RGBA8 out (44) | 19.84  | 20.05 | +1.10% | 483.9 → 483.8 |
| 2   | `jxl-decode`, RGBA8 out (44) | 19.99  | 20.27 | +1.41% | 483.9 → 483.8 |

Both runs are inside the ±1.5% an A/A run measured
(`jxl-speed4-20261103.md`), but both are positive: run 2 (12 rounds) has
three rows faster at p < 0.05 (kodim23 +3.1%, the 1152×858 wikipedia
photo +4.3%, a 16×16 icon +0.9%) and none slower, and the large photos'
medians all rise (the 50-megapixel mosaic 34.23 → 34.97 MP/s, p = 0.07).
The converter's narrowing was a small share of a lossy decode, so this is
the most it could give. Peak RSS does not move: the stack buffer is
skipped, not freed.

Exactness: the decoder's output to each 8-bit format was compared with
its native output converted by `image.convert` (which is what the old
path wrote), on the first frame of the 303 JPEG XL files in `corpus/` and
`bench/corpus-gen/` (192 rgb16, 48 rgba16, 11 gray16, and one
rgba16_premul native, the rest 8-bit native): `rgba8`, `rgb8`,
`rgba8_premul`, `gray8`, `gray_alpha8`, `gray_alpha8_premul`, and `bgra8`
all agree on every byte (`jxl-dst8-20261104/exact.txt`).

Method: the bench's `jxl-decode` writes RGBA16, so both builds were
measured with a local change to `bench/zig/jxl.zig` that writes RGBA8
for that operation (`jxl-dst8-20261104/bench-op.diff`, not committed).
`bench-image serve` builds side by side on the last core (`taskset -c 3`),
loops sized once (`BENCHTIME_MS=50`), 8 and 12 rounds alternating which
build goes first per row, benchstat (median MP/s, Mann-Whitney U), and
GNU time's peak RSS per size class. Both builds checksum the same
on every row.

Machine: Intel Xeon Processor @ 2.60GHz (Ice Lake, 4 vCPUs, AVX-512, a
shared cloud host), Linux 6.1, Zig 0.16.0. Base: main 6cf7a57.

Raw output in `jxl-dst8-20261104/`: `lossy-*` is run 1 and `lossy2-*`
run 2.
