# JPEG XL lossless encode, stage 2, 2026-11-02

Stage 2 of `image.jxl.encode` (`wave5-jxl-encode2`), in the order the
owner set: the oracle's time in oracle-ci, then tree learning's memory up to
a megapixel and its speed on icons, then photos. Stage 1 is
`jxl-encode-20261102.md`; docs/slop/jxl-encode.md has the design.

| commit  | change                                                                                                      |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| oracle  | jxl_encode's oracle encodes smaller sources                                                                 |
| speed   | counting sorts for thresholds, nonzero masks for the split scan, 15 color-transform channels instead of 126 |
| buckets | samples keep a byte per property; thresholds come from a first, random pass                                 |
| leaves  | fast's tree may grow to 256 leaves (was 64), default's to 2048 (was 512)                                    |

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host, so only paired ratios are steady), Linux 6.1, Zig 0.16.0 ReleaseFast
for this CPU; libjxl 0.12.0, `cc -O3 -march=native`, one thread.

## Oracle

`test/oracle/jxl_encode.zig` generates its inputs serially, under the
comparison's lock, and the encoder's time on them was most of jxl_encode's
192 s in oracle-ci (20,000 inputs). Sources were up to 64×64, one in 16 up
to 320×200, at fast (4/8), default (3/8), or best (1/8, up to 32×32). Now
they are up to 24×24, one in 32 a strip 257 to 320 long and up to 24
across (two groups, in either direction; fast 7/8 of those), with best
only up to 16×16. Same efforts otherwise.

`just oracle 20000 1 jxl_encode` on main's encoder with the new oracle
file, in a worktree, nothing else running: 45.7 s and 47.7 s, 15,009
comparable, 0 mismatches. Up to 32×32 it took 62.7 s and 61.6 s.

## Method

Two kinds of measurement:

- **Corpus totals** (`jxl-encode2-20261102/corpus/`): a scratch program
  encoding each of the 43 files of `bench/corpus-gen/jxl_encode` once (20
  times for icons), pinned to one core, through `corpus.sh`, and the byte
  count and an md5 of each file. These steered the changes and give the
  sizes; their times are single runs, often beside other work.
- **A/B** (`run.sh`): `convert-tails-20261102/ab.sh`, the bench-compare
  method with arms given as binaries: checksums, peak RSS of one pass, then
  5 rounds that time every arm on a row back to back in a rotating order,
  pinned to one core. Each change's `bench-image` against the one before,
  beside libjxl, on `jxl-encode-e3`, `e7`, and `e8` (our fast, default,
  and best); leaves and shared on e3 and e7 only, since best's files and
  code did not change. Speed and buckets ran one after the other on core
  3; leaves and shared ran at the same time, on cores 2 and 1. A ratio
  is this build's throughput over the arm's: the geometric mean over a
  class's rows of each row's median paired ratio. Classes as
  bench-compare's: icons (at most 4096 pixels, 13 rows), up to a megapixel
  (23), larger (7).

## Speed

Profiles of 16×16 and 64×64 icons put the time in tree learning: sorting
each property's sample values to choose thresholds (36% of a 16×16 fast
encode), the color transform search (16%, most of it the 42 transforms'
code, unrolled), and at default and best the split scan, which visits
every token of every bucket and predictor though few are nonzero in a
small node. The changes, none of which changes a file (every corpus file
and bench row is byte for byte the same at every effort):

- Thresholds: a property whose sampled values span fewer than 4096 is
  sorted by counting.
- Split scan: each row of counts carries a 64-bit mask of its nonzero
  tokens, and the scan walks the mask.
- Color transforms: the 126 channels of the 42 transforms are 15 distinct
  functions of R, G, and B. Each is scored once, and a transform costs
  its three channels' sum.

A/B (`speed/summary.txt`), this build over the one before:

| effort            | icons | ≤1 MP | >1 MP |
| ----------------- | ----- | ----- | ----- |
| fast (e3 rows)    | 1.64  | 1.04  | 1.00  |
| default (e7 rows) | 1.34  | 1.03  | 1.01  |
| best (e8 rows)    | 1.18  | 0.97  | 0.99  |

At best up to a megapixel, 5 of 23 rows are slower (the slowest 0.88,
`20XX_Menu_picture`): with 14 predictors the masks cost more to keep than
they save in the scan on large nodes.

## Buckets: learning memory

Stage 1 kept every sample's properties as i32 (16 plus four per reference
channel: 100 bytes a sample at default with its 4 predictor tokens, 126 at
best), and learning added a byte per property for buckets and sort scratch.
By the work-memory formulas that was about 34 MiB at default (2^18
samples) and 81 MiB at best (2^19).

Now a sample keeps a byte per property, its bucket. The thresholds must be
known first. An image of at most 2^15 samples is sampled once with whole
properties and bucketed afterwards, as before, so its file is unchanged. A
larger one is sampled twice over the same rows: first one pixel in `cap /
4096` at random, with whole properties (`thresholdSamples(cap)` of them),
to choose thresholds from; then every sampled pixel, bucketed as it is
taken.

Peak RSS of one 1024×1024 RGB encode in the scratch program (`/usr/bin/time`,
including the 3 MiB source and the written file):

| effort  | before   | after    |
| ------- | -------- | -------- |
| fast    | 24.5 MiB | 24.5 MiB |
| default | 43.1 MiB | 23.8 MiB |
| best    | 92.0 MiB | 35.0 MiB |

fast never kept many samples (2^15); its memory is the token store and the
output, as at default now.

Sizes: the first pass chooses thresholds from different samples than
before, which moves files either way by a few tenths of a percent. Corpus
totals against stage 1: fast unchanged (every corpus file has at most 2^15
fast samples), default 14,768,073 bytes (+0.16%), best 14,350,801 (−0.41%).
The first pass as first written took a strided one pixel in 512 at best,
which lands in the same column of a 256-wide group; best came out 0.61%
larger (`mem2`, `mem5`), and the random pass fixed it. Drawing the first
pass from 16 streams' narrower bands instead (`mem`, not kept) made fast
1.6% larger. A 16,384-sample first pass (`mem4`) was no better than 4096.

A/B (`buckets/summary.txt`), this build over the one before; 60 of 129
rows' files differ:

| default (e7 rows) | 1.03  | 1.00  | 0.96  |
| best (e8 rows)    | 1.00  | 0.98  | 1.00  |

Peak RSS of a pass over the corpus (`buckets/rss.txt`, the largest file

## Shared

The decoder's `Predictor`, `neighbours`, `predictOne`, `Wp`, and
`initAlias` (made pub in 638be00) replace the encoder's copies. Every
corpus file at every effort and every bench row is unchanged. A/B
(`shared/summary.txt`): 1.00 on every class at fast; at default 1.01,
0.99, and 1.00, with 4 of 23 rows up to a megapixel slower (the slowest
0.92). A guess, not measured: the decoder's weighted predictor reads its
parameters from its header at run time, where the copy had them as
constants.
