# JPEG for TIFF: the CMYK converter only for CMYK, 2026-11-02

While adding `Decoder.workLen` and `Options.crop` for TIFF's JPEG
(docs/slop/jpeg.md), an A/B on the baseline icons showed the CMYK switch
(results/jpeg-cmyk-20261102.md) had made every decode build its `cmyk8` to
RGB converter, CMYK or not: `Converter.init` picks a kernel, which a 16×16
icon notices. It is now built only for CMYK and YCCK images. Neither TIFF
change touches a hot path (the output row's width now comes from the
destination, which is the frame's width without a crop).

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512, a shared cloud
host), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU. The baseline row's
15 icons (16 to 512 pixels square, `bench/corpus-gen/jpeg/baseline`),
interleaved, 10 rounds of each binary alternately, pinned with `taskset -c
2`, `BENCHTIME_MS=40`. Before is the decoder before the CMYK switch (main
at 0d94f97), after is this branch with both TIFF changes:

benchstat geomean 178.1 to 186.3 MP/s, +4.64%, no row significantly
slower (p ≥ 0.19 on all but one, which is 13% faster). Raw output in
`jpeg-tiff-20261102/`: `icons-before.txt`, `icons-after.txt`, and
`icons-benchstat.txt`.

`just bench-compare 10 jpeg-decode jpeg-decode-cmyk` on this branch (rebased
on main at 49f25d6) shows the rows where they were: baseline against
libjpeg-turbo 5.66× on icons, 1.18× up to 1 MP, 1.03× above (stage 1:
5.08, 1.19, 1.03); CMYK 3.72, 1.35, 1.26 (the CMYK switch: 3.68, 1.37,
1.21). libjpeg-turbo and Wuffs checksum the same on all 88 rows. Raw output:
`bench-summary.txt` and `bench-benchstat.txt`.
