# JPEG XL lossless encode, stage 8, 2026-11-03

Stage 8 of `image.jxl.encode` (`wave5-jxl-encode8`): fewer bytes per
learning sample, after decision 75 grew default's samples to 2^20 and
peak RSS with them (125.8 → 142.4 MiB, `jxl-encode7-20261103.md`). Every
file is the same. Method as in `jxl-encode4-20261103.md`.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host, so only paired ratios are steady), Linux 6.1, Zig 0.16.0 ReleaseFast
for this CPU; libjxl 0.12.0, `cc -O3 -march=native`, one thread.

## Where the memory went

A sample was a byte per property (its bucket) and a byte per predictor
(its token), in two arrays, and learning added a 4-byte index per sample
to partition: 24 + 4 + 4 = 32 bytes at default, 28 + 14 + 4 = 46 at best.
Learning's memory is released before the tokens are counted, and the
token store (4 bytes a token, up to 2^22 tokens, 16.8 MB) reuses it, so
the samples set the peak only when they outgrow the store and what comes
after it. At 2^18 samples they did not; at 2^20 (34 MB) they did, by
the 16.6 MiB the bench saw.

## The change

- One row per sample, tokens first, then buckets. A row is bytes, as
  before, unless the image is sampled in two passes and byte rows would
  take more memory than the token store (`packRows`); then each bucket
  takes the bits its effort's thresholds need (5, 6, or 7 for 16, 32, or
  64 thresholds) and each token 6 (tokens are capped at 63 for
  learning). Default's row is 21 bytes packed (28 as bytes), best's 36
  (42).
- No index: learning partitions the rows themselves, with the same swaps
  the index took, so every node sees its samples in the same order and
  judges the same subsample. A node's samples are contiguous, so counting
  reads memory in order.
- Learning is compiled for each bucket width (5, 6, 7, and 8 for bytes),
  so a byte row's bucket is one load, as before, and a packed one a
  two-byte load, a shift, and a constant mask. Sampling packs a row's
  fields with unrolled shifts for each width and property count.
- `workLen` counts learning's parts and the parts made after them (token
  store, histograms, codes) once, the larger, since they share memory. It
  now also counts two things it had covered only by slack: the palette's
  keys, colors, and order and the rows its search reads, and the
  sections' sizes.

A first version read packed fields with the width a variable and packed
them in a loop; it cost default 9–11% on the small synthetic images,
where learning is most of the time (testcard_rgba 256×256, qoi_logo,
3dcursedlabyrinth), and unpacking a row with vector shuffles was slower
still. With the widths compile-time constants those images run at main's
speed (`rows/summary.txt`).

Which images pack: none at fast, whose 2^15 samples are one pass; at
best, every image of more than 2^15 samples (about 91×91), since its 2^19
byte rows (22 MB) outgrow even a full store; at default, from 2^15
samples up to about 680×680, where the store (16 bytes a pixel) passes
2^18 byte rows (7.3 MB), and again from about 2.4 MP, where one in 16 of
the samples outgrows the full store. The 256×256 testcard packs (7.3 MB
of byte rows against a 1 MB store); wikipedia 1276×850 and tecnick
1200×1200 do not.

A bump allocator's high-water mark was checked against the new `workLen`
in a temporary test over 12 sizes from 1×1 to 2100×600, four formats,
three kinds of content, and every effort: every encode fit, the tightest
with 46 KB to spare (1×1 at best).

## Speed

A/B (`rows/summary.txt`), this build over main's, 3 rounds on core 3:

| rows              | icons | ≤1 MP | >1 MP | vs cjxl (icons, ≤1 MP, >1 MP) |
| ----------------- | ----- | ----- | ----- | ----------------------------- |
| fast (e3 rows)    | 1.00  | 0.97  | 1.02  | 0.58, 0.96, 0.79              |
| default (e7 rows) | 1.02  | 1.02  | 1.02  | 0.89, 1.15, 1.22              |
| best (e8 rows)    | 1.06  | 1.10  | 1.07  | 0.35, 0.88, 1.98              |

79 of 129 rows are within noise, 17 slower, the rest faster. Fast's ≤1
MP class is inside its ±4% (3dbrick2 0.83 [0.69, 1.06]); default's
slowest row is 0.87 (a 600×600 PNG, [0.87, 0.97]), and apple.com 0.94.
Best gains most, likely from reading its 36-byte rows in order rather
than gathering 42 bytes a sample through the index.
