# GIF decode against Wuffs and giflib, 2026-11-01

`image.gif.Decoder` against Wuffs, the bar, and giflib, the reference
library, with stb_image, Rust's `gif` crate (through `image`), and Go's
`image/gif` as comparison arms. Two operations (bench/ops.tsv), both
`same`, so every arm's output checksums the same as ours on every row it
has (52 of 52 for Wuffs, giflib, `image`, and Go; 51 for stb):

- `gif-decode`: a whole file from memory per call, the first frame, into
  RGBA8.
- `gif-decode-anim`: every frame composited into the canvas per call, as a
  player does (frame 0 replaces the canvas, later frames blend over it, each
  frame's disposal applied before the next, restore to previous included),
  leaving the last frame. Megapixels are the canvas's, once per call, so a
  12-frame animation's MP/s is about a twelfth of a still's.

Throughput is megapixels per second; a ratio is this package's throughput
over the arm's (above 1, ours is faster), the geometric mean over rows of
each row's median paired ratio over 10 rounds. docs/slop/gif.md has the
decoder's design.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host where rows swing by ±10–30% between rounds, so only paired ratios are
steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native`, Rust `target-cpu=native`, Go `GOAMD64=v3`. Command:
`just bench-compare 10 gif-decode gif-decode-anim` (exit 0). Raw output in
`gif-20261101/`: `summary.txt` (the table bench-compare prints),
`benchstat.txt`, `check.txt` (checksums and skips), `raw-*.txt`, `rss.txt`,
and `rss-by-class.txt`.

Inputs, `bench/corpus-gen/gif/` (bench/corpus/gif.sh, checksums in
bench/corpus/gif.sha256): `still/` is every shared source as ImageMagick
writes a 256-color GIF (dithered, with a transparent index for sources
with alpha), from 16×16 icons to the 50-megapixel mosaic, plus an
interlaced photo and icon (46 files). `anim/` is six animations of the
kinds people meet: the 32- and 64-pixel icons in turn, optimized into
changed-region frames with transparency; a Kodak photo panned (480×320,
12 full frames); a 1280×720 screen recording with a moving highlight,
optimized; an icon moving over a 1600×900 photo, each frame disposed to
previous; and an icon bouncing on a transparent 320×240 canvas, each frame
disposed to background. Size classes: icon ≤ 64², 1mp ≤ 1 MP, large
above.

On the 50-megapixel mosaic we decode at 502 MP/s, Wuffs at 386, giflib at 107. The rows slowest against Wuffs: the 32-pixel icon animation (0.78×),
the transparent bounce animation (0.88×; every frame takes the
transparent-index path, a branch per pixel), and some 64-pixel icons and
textures (0.87× at worst; 4 of the 14 icons are below 1, and 9 are within
noise). Fastest: photos and dithered images with long LZW strings,
1.2–1.9× (kodim01 1.90×, the panned photo 1.68×), where writing table
entries 8 bytes at a time pays. An earlier run of the same code, before
stb had animation rows, gave 1.14× over all rows (0.99, 1.23, and 1.24 on
stills by class): the shared host moves the geomean by a few percent.

stb's anim rows leave out sprite-1600x900.gif: `stbi_load_gif_from_memory`
reads out of bounds and crashes on a frame that restores to previous, so
the stb arm fails such files before calling it (bench/c/stb-gif.c), and
the harness skips the row (`# SKIP`, check.txt). On the other five
animations stb agrees with every arm.

We are the smallest in every class. Our work memory is about 68 KiB for
any image (the LZW table, an 8 KiB index buffer, 4 KiB of compressed data,
and the palette in the destination's format), and the anim operation adds
the region saved for restore to previous. The large class is the 192 MiB
RGBA8 output of the mosaic. stb and `image` allocate their own copy of the
pixels (stb's animation API a whole canvas per frame, hence 59.6 MiB for
three small animations), and Go allocates paletted images per frame.

## The changes measured

The decoder's performance work, measured with interleaved A/B rounds (the
same serve protocol as bench-compare, two builds of bench-image) during
development; numbers are against Wuffs on the final corpus:

- **Table entries hold 8 bytes of the string's tail** (`tail: [4096]u64`,
  `meta: [4096]u32` of prefix and length), so a string is written 8 bytes
  at a time back from its end, and literals are entries too: one loop case
  for both. This is what put us ahead of Wuffs on photos.
- **A packed 12-byte entry** (tail and meta in one struct) was slower: icons
  at 0.4× Wuffs, from unaligned loads stalling on the stores just before
  them. Dropped.
- **The bit accumulator reads 8 bytes ahead**, and the previous code's
  entry stays in registers through the loop; `decode` is `noinline`.
- **The palette is converted to the destination once per color table**, and
  written straight from the file for RGBA8; pixels are a lookup and a store
  specialized on bytes per pixel.
- Per-call setup is not the icon gap: a 1×1 GIF costs 110 ns here and 263
  ns in Wuffs (`perf` on a loop of `check`). Icons are bound by the LZW
  loop on short strings.
