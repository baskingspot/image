# Wave 0 baseline: conversion and QOI decode, 2026-11-01

The first `just bench-compare` runs: `image.convert` against Wuffs's pixel
swizzler (and Go's `image/draw` where it has the pair), and
`image.qoi.Decoder` against Wuffs, qoi.h, Rust's `image` (which uses the
`qoi` crate), and `zune-qoi`. Throughput is megapixels per second; a ratio is
this package's throughput over the arm's (above 1, ours is faster), the
geometric mean over rows of each row's median paired ratio over 10 rounds.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, AVX-512; a shared cloud
host, so rows vary by ±5–25% between rounds and only the paired ratios are
steady), Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native` (GCC from the dev shell), Rust `target-cpu=native`, Go 1.26
`GOAMD64=v3`. Buffers: input at a page boundary, output 2048 bytes past one,
for every arm. Raw output in `baseline-20261101/{convert,qoi}/`
(`config.txt`, `rss.txt`, `benchstat.txt`, `summary.txt`, `rows.txt`, and
every sample in `raw-<arm>.txt`).

## Conversion

Inputs: one photo with alpha (RGBA, 8 and 16 bits) and one Kodak photo (RGB,
gray) at 16×16, 64×64, 256×256, 1024×1024, and 4096×4096.

| image / arm, geomean  | image MP/s ≤64² | vs Wuffs ≤64² | ≤1 MP | >1 MP | vs Go ≤64² | ≤1 MP | >1 MP |
| --------------------- | --------------- | ------------- | ----- | ----- | ---------- | ----- | ----- |
| RGBA8 → BGRA8         | 13780           | 2.11          | 1.22  | 0.93  | -          | -     | -     |
| RGB8 → RGBA8          | 7259            | 1.39          | 1.10  | 1.01  | -          | -     | -     |
| RGBA8 → RGB8          | 8482            | 7.09          | 5.25  | 1.41  | -          | -     | -     |
| RGBA8 → premultiplied | 2143            | 1.35          | 1.32  | 1.15  | 9.74       | 9.09  | 5.70  |
| Gray8 → RGBA8         | 8790            | 1.53          | 1.42  | 1.00  | 15.47      | 11.95 | 2.56  |
| RGBA16 → RGBA8        | 2211            | 0.67          | 0.78  | 1.01  | -          | -     | -     |
| all 30 rows           | 3854            | 1.48          |       |       | 9.10       |       |       |

At 4096×4096 (64 MiB in, up to 64 MiB out) every pair is memory-bound and
ties Wuffs within a few percent. Below that we lead everywhere but 16-bit
narrowing, where we round (c + 128) / 257 and Wuffs takes the high byte; the
outputs differ by design (the operation is `own` in bench/ops.tsv), and the
rounding costs 20–30% on small buffers. Premultiplication also differs from
Wuffs and Go, which agree with each other: both compute in 16 bits and
truncate, and we round c·a/255 exactly.

The first run had RGB → RGBA at 0.25× Wuffs and Gray → RGBA at 0.20×: a
`@shuffle` of a 48- or 16-byte vector into 64 bytes with a constant second
operand compiled to scalar byte moves. Rewriting both as 16-byte shuffles
(one `pshufb` per 16 output bytes) with the alpha ORed in made them 5–11×
and 2.4–5× faster (`bench-image bench`, 200 ms samples on one core:
RGB → RGBA 16×16 645 → 5180 MP/s, 1024×1024 1077 → 3636 MP/s; Gray → RGBA
16×16 1234 → 2936, 1024×1024 1168 → 4813). The table above is after it.

Peak RSS is the same for us and Wuffs on every pair (82–194 MiB, all of it
the input and output buffers); Go's arm adds 23–78 MiB of runtime and
garbage.

## QOI decode

Inputs: the 44 files of `bench/corpus-gen/qoi/`, 16×16 icons to a
50-megapixel photo mosaic (bench/README.md). `qoi-decode` writes each file's
own channels (RGB or RGBA); `qoi-decode-bgra` writes BGRA, which only Wuffs
also offers.

| image / arm, geomean  | rows | image MP/s | Wuffs | qoi.h | image (qoi crate) | zune-qoi |
| --------------------- | ---- | ---------- | ----- | ----- | ----------------- | -------- |
| decode, icons ≤ 64×64 | 13   | 278.5      | 1.15  | 0.87  | 0.59              | 2.22     |
| decode, to 1 MP       | 23   | 275.6      | 1.06  | 1.03  | 0.64              | 1.64     |
| decode, over 1 MP     | 8    | 205.2      | 1.08  | 1.07  | 0.75              | 1.57     |
| BGRA, icons           | 13   | 256.5      | 1.01  | -     | -                 | -        |
| BGRA, to 1 MP         | 23   | 260.0      | 0.98  | -     | -                 | -        |
| BGRA, over 1 MP       | 8    | 199.2      | 1.04  | -     | -                 | -        |

So: ahead of Wuffs (the bar) by 6–15% on native output and level on BGRA,
level with qoi.h (slower on icons, faster on large images), well ahead of
zune-qoi, and behind the `qoi` crate by 1.3–1.7×. On the 50-megapixel mosaic:
121 MP/s, Wuffs 108, qoi.h 109, the `qoi` crate 139, zune-qoi 72. Worst rows
against Wuffs: a 64×64 RGB texture at 0.50× and a 320×240 screenshot at 0.67×.

Peak RSS: 257 MiB for us, Wuffs, `image`, and zune (the inputs plus the
mosaic's 192 MiB of pixels); qoi.h 403 MiB, because its API allocates the
pixels and the arm copies nothing but still holds both. The decoder itself
needs no work memory: 80 bytes of state and 300 bytes of stack.

Where the gap to the `qoi` crate is, from rows.txt and an experiment:

- **Runs.** It is 3× faster on run-heavy images (the QOI logo, transparent
  pngimg files, game screenshots), where we store run pixels one at a time.
  Filling runs with a word `@memset` doubled those rows (+104% to +124%,
  benchstat over 10 interleaved rounds) but cost 3–9% on photos when inlined
  into the chunk loop and more out of line, so wave 0 keeps the simple loop;
  making runs fast without slowing the chunk loop is the first target for
  QOI's wave 1 owner.
- **Per-call setup on icons**: 16×16 decodes take about 0.9 µs, 25–35% behind
  qoi.h and the `qoi` crate; the setup in `decodeConfig` and `decodeFrame`
  (config built twice, the converter choice, the footer) is the next target.
- **Photos**: within 10% of everyone but the `qoi` crate (0.75–0.85×); the
  chunk dispatch's branch order is the place to look.

## How to rerun

```sh
just bench-compare 10 convert-rgba8-bgra8 convert-rgb8-rgba8 convert-rgba8-rgb8 \
  convert-rgba8-premul convert-gray8-rgba8 convert-rgba16-rgba8
just bench-compare 10 qoi-decode qoi-decode-bgra
```
