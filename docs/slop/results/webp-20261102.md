# WebP decode against libwebp, Wuffs, `image`, and Go, 2026-11-02

`image.webp.Decoder` against libwebp 1.6.0, the bar and the oracle, Wuffs
(lossless files only), Rust's `image` (the `image-webp` crate), and Go's
`golang.org/x/image/webp`. Every arm decodes a whole file from memory per
call into RGBA8, and every arm's output checksums the same as ours on every
row it decodes. Throughput is megapixels per second; a ratio is this
package's throughput over the arm's (above 1, ours is faster), the geometric
mean over rows of each row's median paired ratio over 10 rounds.
docs/slop/webp.md has the decoder's design.

Machine: Intel Xeon Processor @ 2.60GHz (4 vCPUs, a shared cloud host),
Linux 6.1, Zig 0.16.0 ReleaseFast for this CPU; C arms `cc -O3
-march=native`, Rust `target-cpu=native`, Go `GOAMD64=v3`. Inputs:
`bench/corpus-gen/webp/` (bench/corpus/webp.sh): every source of the bench
corpus as `cwebp` writes it with its defaults, lossless (`-lossless`) and
lossy (quality 75, with ALPH for sources with alpha).

## Stage 1: lossless (VP8L)

`webp-decode-lossless`, 43 files, and `webp-decode-lossless-large`, the
50-megapixel mosaic alone: its file names 278 prefix code groups, more than
the 256 Wuffs reads, so Wuffs's arm leaves it out, and a row Wuffs fails
cannot share an operation with rows it passes. Raw output in
`webp-20261102/lossless/`.

| rows (count)     | image MP/s | vs libwebp | vs Wuffs | vs `image` | vs Go |
| ---------------- | ---------- | ---------- | -------- | ---------- | ----- |
| icons ≤ 64² (13) | 40.0       | 1.46       | 2.04     | 1.14       | 3.87  |
| to 1 MP (23)     | 108.3      | 0.88       | 2.61     | 1.40       | 2.86  |
| over 1 MP (7)    | 81.0       | 0.91       | 2.57     | 1.45       | 2.49  |
| 50 MP mosaic (1) | 45.4       | 0.97       | -        | 1.30       | 1.91  |
| all (44)         | 75.5       | 1.03       | 2.41     | 1.32       | 3.03  |

libwebp's own throughput, from those ratios: about 27 MP/s on icons, 123 to
1 MP, 89 over 1 MP, and 47 on the mosaic. We win on icons (no per-call
allocation or thread setup) and lose most on color-indexed images with
flat areas, where libwebp's palette fast paths reach 550–760 MP/s:
0.54× on the 343×480 maze screenshot, 0.57× on the 600×600 pngimg, and
0.73–0.80× on the small texture, the QOI logo, and the long web screenshots.

**Peak RSS** of one pass over each operation's inputs (GNU time, MiB; the
inputs and output buffers every arm holds alike, plus what the library
allocates):

| operation                  | image | Wuffs | libwebp | `image` | Go    |
| -------------------------- | ----- | ----- | ------- | ------- | ----- |
| webp-decode-lossless       | 40.0  | 67.5  | 72.2    | 99.7    | 244.3 |
| webp-decode-lossless-large | 232.2 | -     | 422.5   | 567.7   | 458.1 |

Ours is the caller's work buffer: only the pages a file touches count, so
the bound `work_len` states (26 MiB of prefix tables for a megapixel) costs
nothing it does not use; on the mosaic we hold the 192 MiB canvas and a
ring of about 4 MiB of pixels, and libwebp about one more canvas-sized
buffer.
